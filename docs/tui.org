* The =ai-tui= front-end
=ai-tui= drives any ai-glib provider from a terminal, showing prose,
reasoning and grouped tool calls as they happen. It is what
[[file:cli.org][the =ai= CLI]] is for one-shot prompts, but for sitting in.

Everything about *what* a conversation is --- how calls group, how a summary
reads, which run of bytes is a filename --- lives in
[[file:transcript.org][the view layer]]. This binary turns a style role into
an ncurses attribute, puts characters on a screen, and reads keys. That is
the whole of it, and it is deliberate: an Emacs front-end replaces this one
file and shares everything else.

** Synopsis
#+begin_src sh
ai-tui [-p PROVIDER] [-m MODEL] [-s SYSTEM] [OPTIONS]
#+end_src

#+begin_src sh
ai-tui -p claude-code -m opus
#+end_src

** What it looks like
#+begin_example
> build phase 1

Now the codec registry.

Created 2 files  +5-0 ›

Cleaning up a clumsy double-lookup.

Edited cmacs-office-package.c, ran 2 commands  +9-12 ›

1200 in / 340 out  $0.0182
#+end_example

The alternation is the point. Narration, a collapsed group of what the model
actually did, more narration --- rather than a wall of tool output with the
explanation lost inside it.

** Options
| Option                | Description                                              |
|-----------------------+----------------------------------------------------------|
| =-p=, =--provider=    | Provider name; defaults to =$AI_PROVIDER=, else =claude=  |
| =-m=, =--model=       | Model id                                                 |
| =-s=, =--system=      | System prompt                                            |
| =--effort=            | Reasoning effort: =low= … =max= (CLI providers)          |
| =--max-tokens=        | Cap per response, default 4096                           |
| =--no-stream=         | Wait for each whole turn instead of streaming it         |
| =-c=, =--continue=    | Continue the provider's most recent session              |
| =--skip-permissions=  | Let a wrapped CLI run its tools without asking           |
| =--local-tools=       | Run tools in this process (HTTP providers only)          |
| =-y=, =--yes=         | Approve every local tool call without asking             |
| =--set PROP=VALUE=    | Set any provider property; repeatable                    |
| =--no-agents=         | Do not let the model start background agents             |
| =--dump PROMPT=       | Run one turn with no terminal and print the transcript   |
| =--width N=           | Wrap width for =--dump= (0 for none)                     |
| =--dry-run=           | Print the command a CLI provider would run, then exit    |
| =-v=, =--version=     | Print the version                                        |
| =--license=           | Print licensing information                              |

=--set= is provider-property reflection, exactly as in =ai=: a provider that
grows a knob is reachable immediately with no flag added here. An unknown
name is an error rather than a silent no-op, and so is a value that does not
parse --- a run that quietly ignored the bound you asked for is worse than
one that refuses to start.

** Keys
| Key              | Does                                              |
|------------------+---------------------------------------------------|
| =Enter=          | New line --- or take the completion, if one is open |
| =C-d=            | Send. On an empty line, quit                      |
| =Alt-Enter=      | Send                                              |
| =C-g=            | Edit the prompt in =$EDITOR=                      |
| =C-c=            | Stop the turn in flight --- never the program     |
| =Up= / =Down=    | Walk the input history, or the completion menu     |
| =Left= / =Right= | Move the cursor                                   |
| =C-a= / =C-e=    | Start / end of line                               |
| =C-u=            | Clear the input                                   |
| =PgUp= / =PgDn=  | Scroll the transcript, or page the completion menu |
| =Tab=            | Take a completion, or step to the next            |
| =Escape=         | Dismiss the completion menu                       |
| =C-n=            | Select the next tool or reasoning block           |
| =C-b=            | Expand or collapse the selected block             |

=C-c= cancels the turn rather than killing the process, because in a harness
"stop what you are doing" is what you almost always mean. Quitting is =C-d=
on an empty line, or =/quit=.

*** Why =Enter= is not send
A prompt worth writing is usually more than one line, and a chat box that
sends on =Enter= makes writing one an exercise in not pressing the wrong
key.

The obvious alternative --- =Enter= sends, =Shift-Enter= inserts --- is not
available: a terminal sends one carriage return for both, and the
harnesses that bind them differently ship a terminal-configuration step
to make the two distinguishable. Rather than require that, the common key
does the common thing and sending is =C-d=, which has meant "that is all
my input" in every shell there has ever been. =Alt-Enter= sends too, for
the muscle memory.

While the input has anything in it, the status bar says so.

The input grows as you type, up to ten rows, and continuation rows carry
a =│= marker so a wrapped prompt reads as one thing. Past ten rows it
scrolls rather than eating the screen --- at which point =C-g= is the
better tool.

*** =C-g=: write it in your editor
Writes the current prompt to a temporary =.md= file, hands the terminal
to =$VISUAL= or =$EDITOR=, and takes back whatever was saved. =VISUAL=
wins because that is what the two mean: it is the full-screen one, and
this needs a screen. Both are parsed as command lines, so =EDITOR="emacs
-nw"= works.

*Quitting the editor without saving leaves the prompt alone.* A non-zero
exit is how somebody says they changed their mind, and the file on disk
may be a half-finished draft --- reading it back anyway would make the
cancel do the opposite of cancelling.

One trailing newline is stripped, since every editor that ends a file
properly adds one. Interior blank lines are kept exactly as written.

The turn keeps running while the editor is open. Nothing repaints ---
this process is blocked --- but callbacks queue up and are dispatched the
moment the editor exits.

Scrolling away from the bottom stops the view following new output; the
status bar says =[scrolled]= while that is so. Sending, or scrolling back
down, resumes following.

** Completion
The menu opens as you type. A =/= at the start of the line lists every
command, skill and agent, and each character after it narrows the list;
an =@= anywhere lists paths.

| Key                | Does                                            |
|--------------------+-------------------------------------------------|
| =Up= / =Down=      | Move the highlight, wrapping at both ends       |
| =PgUp= / =PgDn=    | Move it a page at a time                        |
| =Tab=              | Take what is on offer, or step to the next      |
| =Shift-Tab=        | Step back                                       |
| =Enter=            | Accept the highlighted candidate                |
| =Escape=           | Dismiss, until the line changes again           |

The arrows, =PgUp= and =PgDn= belong to the menu while it is showing and
to the input history and the transcript when it is not --- one key, two
jobs, decided by what is on screen. Press =Escape= first if you want the
history back with a half-typed command still on the line.

Each row is the name in bold, its description dimmed, and the harness it
came from right-aligned --- the origin has its own column because the
description is what gets truncated, and the origin is the half that tells
two same-named commands apart.

=Tab= inserts a single candidate outright. With several it inserts their
common prefix if that adds anything, and steps the highlight otherwise
--- so the first =Tab= makes progress and the second is a choice rather
than a repetition. Directories carry a trailing slash, so one more =Tab=
walks into them.

Mentions and command names are highlighted as you type, using the same
scanner the pipeline uses. A mention that will not resolve still lights
up --- it is a candidate, and you can see it was noticed.

None of this is decided here: =ai_completion_context_query()= returns the byte
range to replace and the candidate list, and this program does the
replacing. An Emacs frontend will call the same function. See
[[file:harness.org][the harness layer]].

** Commands
The built-ins, plus every command, skill and agent found in the
directories the other harnesses use. =/help= lists all of it with origins.

| Command             | Does                                              |
|---------------------+---------------------------------------------------|
| =/help=             | Every command, skill and agent, and the keys      |
| =/clear=            | Empty the transcript, the history and the todos   |
| =/quit=             | Exit                                              |
| =/model [NAME]=     | Show or switch the model without restarting       |
| =/provider=         | Show the provider                                 |
| =/tools=            | The tools the model can call                      |
| =/commands=         | Commands from disk, and what shadows what         |
| =/skills=           | Skills                                            |
| =/agents=           | Agents                                            |
| =/reload=           | Rescan the search paths                           |
| =/cwd [PATH]=       | Show or change the working directory              |
| =/todos=            | The current todo list                             |
| =/running=          | Background agents, and what they are doing        |
| =/kill ID\vert all=      | Stop a background agent, or every one             |
| =/expand LINE=      | What a line would send, without sending it        |
| =/save PATH=        | Write the transcript to a file                    |

=/agents= and =/running= are different things: the first lists agent
*definitions* found on disk, the second lists agents actually running.

Anything else is a command file: =/deploy staging= runs
=~/.claude/commands/deploy.md= with =staging= as =$1=. See
[[file:commands.org][authoring them]].

=/clear= empties the *local* view. A provider holding a session of its own
--- the CLI wrappers do --- is not affected; clearing the transcript does
not un-say what was already said to it.

*** When a command is not found
=/commands= with nothing to show prints every directory it searched,
which is the answer to the question you are about to ask. If a file is
there but another one won, the same listing prints the winner's path.

*** CLI providers handle their own
claude-code, opencode and grok resolve =@=, =/= and their own skills
themselves, so with one of those selected a line reaches the child
exactly as typed and =/compact= still means what it means to them. The
built-ins above still run locally --- the wrapped tool has no opinion
about this program's transcript.

=--no-expand= turns the pipeline off entirely, for the case where the
text must reach the model verbatim.

** Mentions
=@path= pulls a file in. The prompt keeps its shape and the files follow
it, so a one-line question is not buried under the file it named.

#+begin_example
  > explain @src/core/ai-event.c and @src/core/ai-event.h
#+end_example

A directory expands to a listing, a binary file is named but not inlined,
and a path that does not exist is left exactly as written --- which is
what makes an email address or a Python decorator harmless. Use =/expand=
to see the result before sending it.

** While a turn is running
The status bar shows what the turn is doing, with a spinner and the time
so far:

#+begin_example
  Grok Build / grok-4.6   ⠹ Running make test… (5s · ^C to stop)
#+end_example

The phrase tracks the turn --- =Waiting for the model=, =Thinking=,
=Reading ai-event.c=, =Running make test=, =Responding= --- so a long
tool call is visibly a long tool call rather than a program that might
have hung. The elapsed time is what separates a slow turn from a stalled
one.

The words come from =AiConversation:activity=; only the animation lives
here. See [[file:transcript.org::*Showing progress][Showing progress]].

A provider that emits no events (claude-tmux reads a finished transcript
rather than a stream) shows =Waiting for the model= throughout, which is
honest, and is the case where the indicator earns its keep.

** Tool approval
With =--local-tools= against an HTTP provider, tools run in this process and
each call is offered for approval:

#+begin_example
 run Bash: rm -rf build/ ?  [y]es  [n]o  [a]lways  [d]eny all
#+end_example

| Answer      | Does                                                        |
|-------------+-------------------------------------------------------------|
| =y=         | Run this call                                               |
| =n=         | Refuse it; the model is told, and usually tries something else |
| =a=         | Run it, and stop asking about this tool for the rest of the run |
| =d=         | Refuse and abort the turn                                   |

=--yes= approves everything without asking, which is what you want for an
unattended run and not much else.

Refusing one call does not end the turn. The model is told the tool was
denied and generally acknowledges it and tries another route, which is more
useful than a turn that simply stops --- only =d= stops everything. An
answer of =a= is remembered for that run only: consent given about one task
is not consent for the next.

*This never appears for the CLI wrapper providers.* claude-code, opencode
and grok-build run their own tools inside their own processes, and their
approval is =--skip-permissions= and the per-provider =permission-mode= and
=allowed-tools= properties, not this. =--local-tools= is refused for them,
with a note saying so, rather than silently doing nothing.

** =--dump=, and testing
#+begin_src sh
ai-tui -p grok-build --dump "list the files here"
#+end_src

Runs one turn with no terminal at all and prints the transcript as plain
text. That is how the TUI is tested --- =tests/test-ai-tui.c= drives the
whole path from argv through the NDJSON parser, the event stream, the
folding and the summariser against a stub =grok=, with no network and no
tty, and asserts the grouped summary line comes out with the narration in
the right order around it.

It is also the right thing to reach for in a script:

#+begin_src sh
ai-tui -p claude-code --dump "summarise the diff" --width 72 > review.txt
#+end_src

Started without a terminal and without =--dump=, =ai-tui= says so and exits
rather than starting ncurses on a pipe.

** Building
=ai-tui= needs =ncursesw=; the library itself does not. Without it the
binary is dropped from the build with a notice and its tests skip
themselves, so a machine with no terminal library still gets a green suite
for everything else.

On Fedora and its derivatives:

#+begin_src sh
ncurses-devel
#+end_src

The library is linked statically into the binary, as with =ai=, so the
installed =ai-tui= has no runtime dependency on =libai-glib=.

** Notes
- Keys arrive through the main loop (=g_unix_fd_add=), not a blocking read,
  so the provider's I/O continues while you type.
- A terminal resize re-wraps every block at the new width. That is a
  re-render, not a re-derivation: the library caches renderings per width.
- Redraws are coalesced onto an idle. A streamed reply fires a change per
  token, and redrawing on each would spend the whole turn in refresh.
- =claude-tmux= works here, but produces its answer in one piece: it reads a
  finished transcript rather than a stream, so there is nothing to show
  along the way. See the coverage matrix in [[file:events.org][the event stream]].
