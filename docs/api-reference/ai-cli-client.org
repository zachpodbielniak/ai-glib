* AiCliClient
=AiCliClient= is the derivable base class behind every provider that wraps a
command-line coding agent: [[../providers/claude-code.org][Claude Code]], [[../providers/claude-code-tmux.org][Claude Code (tmux)]], [[../providers/opencode.org][OpenCode]],
[[../providers/grok-build.org][Grok Build]], [[../providers/antigravity.org][Antigravity]] and [[../providers/cursor.org][Cursor]]. It is the CLI-side counterpart to [[file:ai-client.org][=AiClient=]], which is the base
for the HTTP providers.

A subclass says *what command to run and how to read its output*; the base
class owns everything else — resolving the executable, piping the prompt,
spawning with a timeout, checking how the process ended, and handing the
output back to the subclass to parse.

** Class Hierarchy
#+begin_example
GObject
  AiCliClient          (derivable)
    AiClaudeCodeClient (final, AiProvider, AiStreamable)
    AiClaudeTmuxClient (final, AiProvider)
    AiOpenCodeClient   (final, AiProvider, AiStreamable)
    AiGrokBuildClient  (final, AiProvider, AiStreamable)
#+end_example

The interfaces live on the subclasses rather than here, because what a
given CLI supports varies — the tmux provider, for instance, has no
streaming mode.

*** The working directory is the security boundary
Every permission mode that can write can write anywhere the process can
reach. The permission flags decide whether the model is *asked*; the
working directory decides what it can *touch*.

#+begin_src C
ai_cli_client_set_working_directory(AI_CLI_CLIENT(client), "/srv/project");
#+end_src

*** Effort level
One property, three spellings:

| Provider   | Flag                  | Vocabulary                              |
|------------+-----------------------+-----------------------------------------|
| claude-code | =--effort=           | low, medium, high, xhigh, max           |
| opencode    | =--variant=          | provider-specific (e.g. high, max, minimal) |
| grok-build  | =--reasoning-effort= | low, medium, high, xhigh (=max= folds onto =xhigh=) |
| antigravity | =--effort=           | low, medium, high (=xhigh= and =max= fold onto =high=) |
| cursor      | (none)               | Effort is baked into the model id; =model-params= holds bracket overrides |

*** Timeouts
=process-timeout-ms= bounds =ai_cli_client_chat_sync()= only. The async and
streaming paths are built on =g_subprocess_communicate_utf8_async()= and run
unbounded; pass a =GCancellable= if you need to be able to stop them.

A zero default would mean an unbounded wait, which is the hang class that
can pin a caller forever — hence the 30-minute default rather than none.

** The synchronous pipeline
=ai_cli_client_chat_sync()= is what a subclass gets for free:

1. resolve the executable — the =executable-path= property, else the
   subclass's =get_executable_path= vfunc (usually an environment variable,
   else a name to find on =$PATH=). A miss is =AI_ERROR_CLI_NOT_FOUND=;
2. call =build_argv=;
3. call =build_stdin=, if the subclass implements it;
4. overwrite =argv[0]= with the resolved path — the subclass emits a
   *placeholder* program token, which is why its argv starts with a bare
   name;
5. spawn, applying =working-directory= through a =GSubprocessLauncher=;
6. communicate, bounded by =process-timeout-ms= — expiry kills the child
   and fails with =AI_ERROR_TIMEOUT=;
7. decide what happened, then call =parse_json_output=.

*** Step 7: the exit status is not the whole story
A failing CLI usually explains itself in its own output format before it
exits. So on a *non-zero* exit with output on stdout, the subclass's parser
is given first refusal: if it recognises the output as a structured error,
that message is what the caller gets. Only its =AI_ERROR_CLI_EXECUTION=
verdict is taken — a non-zero exit still fails the call whatever the
process managed to print.

Without that, an opencode failure surfaced as its raw JSON error event
(with an empty stderr next to it) rather than the sentence inside it.

The converse also happens: a CLI can report an error and still exit *zero*.
grok does exactly that for a rejected argument. There the output parses as
an error object and the parser is what catches it, which is why every
subclass's =parse_json_output= should check for its CLI's error shape
before anything else rather than trusting the status.

** Virtual Methods
#+begin_src C
struct _AiCliClientClass
{
    GObjectClass parent_class;

    gchar *      (*get_executable_path)(AiCliClient *self);
    gchar **     (*build_argv)         (AiCliClient *self, GList *messages,
                                        const gchar *system_prompt,
                                        gint max_tokens, gboolean streaming);
    AiResponse * (*parse_json_output)  (AiCliClient *self, const gchar *json,
                                        GError **error);
    gboolean     (*parse_stream_line)  (AiCliClient *self, const gchar *line,
                                        AiResponse *response,
                                        gchar **delta_text, GError **error);
    gchar *      (*build_stdin)        (AiCliClient *self, GList *messages);
    AiResponse * (*chat_sync)          (AiCliClient *self, GList *messages,
                                        GCancellable *cancellable,
                                        GError **error);

    gpointer _reserved[6];
};
#+end_src

=chat_sync= is an escape hatch for a provider that cannot use the pipeline
at all; only the tmux client overrides it. The other five are the normal
surface.

** Implementing a CLI provider
See [[../contributing.org][Contributing]] for the full checklist. The conventions that matter most:

- *Pipe the prompt, do not pass it.* A conversation in argv hits =ARG_MAX=
  and shows up in =ps=. Emit a placeholder at =argv[0]=, put the prompt in
  =build_stdin=, and have the CLI read it back (=--prompt-file /dev/stdin=,
  or its own stdin handling).
- *Expose every knob as a GObject property.* That is what makes it reachable
  from bindings and from =ai --set= with no extra plumbing.
- *Gate mode-specific flags on the mode*, rather than trusting the caller to
  remember that, say, =--include-partial-messages= is only valid with
  streaming output.
- *Share the "how to run" flags* between =build_argv= and any re-prompt or
  retry path, so a follow-up runs with the same agent, directory and
  permission posture as the turn it follows.
- *Expose the argv builder through a private =-internal.h=* (guarded on
  =AI_GLIB_COMPILATION=, kept out of =PUBLIC_HEADERS=) so tests can assert
  the command line without spawning anything. =ai --dry-run= does not need
  it — it reaches =build_argv= through this vtable.

* Streaming, and the shared reader
Streaming is implemented once, in =AiCliClient=. A subclass implements
=AiStreamable= by forwarding to it and contributing a parser:

#+begin_src C
static void
my_client_chat_stream_async (AiStreamable *streamable, GList *messages,
                             const gchar *system_prompt, gint max_tokens,
                             GList *tools, GCancellable *cancellable,
                             GAsyncReadyCallback callback, gpointer user_data)
{
    ai_cli_client_stream_run_async (AI_CLI_CLIENT (streamable), messages,
                                    system_prompt, max_tokens,
                                    cancellable, callback, user_data);
}
#+end_src

=ai_cli_client_stream_run_async()= resolves the executable, builds the argv,
writes and closes stdin, reads stdout line by line, translates each line
through @parse_stream_events, publishes the results, enforces
=process-timeout-ms=, and assembles the final =AiResponse=.

Before this existed, claude-code, opencode and grok-build each carried their
own copy of that loop --- around 250 lines apiece --- and they had drifted.
Only one failed the task when a line failed to parse; the others read on to
EOF and returned the empty response that produces, so a CLI reporting an
error mid-stream looked like a successful empty answer. And none of them
enforced the process deadline the synchronous path has always had.

* The vfuncs
Two of the class's reserved slots are now used.

** parse_stream_events
#+begin_src C
gboolean (*parse_stream_events) (AiCliClient  *self,
                                 const gchar  *line,
                                 AiResponse   *response,
                                 GPtrArray    *out_events,
                                 GError      **error);
#+end_src

The richer successor to @parse_stream_line: append zero or more
[[file:ai-event.org][AiEvent]] to @out_events instead of returning one delta
string. Return %FALSE only for a real failure --- an unrecognised line is
not one.

Leaving it %NULL still works; the default wraps @parse_stream_line and can
therefore only ever report text, which is exactly how these wrappers behaved
before events existed.

=ai_cli_client_events_to_delta()= goes the other way, so a subclass can
implement the richer vfunc as its single source of truth and still answer
the older contract. Every shipped provider does that, and a test asserts the
two agree.

** spawn
#+begin_src C
GSubprocess * (*spawn) (AiCliClient          *self,
                        const gchar * const  *argv,
                        GSubprocessFlags      flags,
                        GError              **error);
#+end_src

The default honours =working-directory=. Override it only to add something
else to the launcher --- =AiOpenCodeClient= is the one that does, for
=OPENCODE_PERMISSION=, and overriding here means it gets that on the
synchronous path too rather than only when streaming.

Call it through =ai_cli_client_spawn()=, never directly.
