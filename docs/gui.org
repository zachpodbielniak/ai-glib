* The =ai-gui= desktop client
=ai-gui= is a GTK4/libadwaita front-end over the same model
[[file:tui.org][=ai-tui=]] draws in a terminal: one #AiConversation per session,
[[file:transcript.org][the view layer]] deciding what a block is, and
[[file:harness.org][the harness layer]] resolving =@= mentions and =/= commands.

The split matters more than the toolkit. Everything about *what* a
conversation is --- how tool calls group, how a summary reads, which run of
bytes is a filename --- lives in the library. What lives in =gui/= is turning
an =AiStyleTag= into a Pango attribute, putting widgets on a screen, and
reading input. That is the same contract the ncurses front-end honours, which
is why the two agree about a transcript without sharing a line of rendering
code.

Nothing in =LIB_SOURCES= links GTK, deliberately: a daemon, an Emacs module
or a server has to be able to embed ai-glib without dragging in a toolkit.
=gtk4= and =libadwaita-1= are pulled in by the =gui= target alone, and the
binary is dropped --- loudly, once --- when they are absent, exactly as
=ai-tui= is dropped without ncursesw.

** Synopsis
#+begin_src sh
ai-gui [-p PROVIDER] [-m MODEL] [-s SYSTEM] [OPTIONS]
#+end_src

#+begin_src sh
# Open on the saved ai-gui defaults
ai-gui

# A specific provider and model
ai-gui -p claude-code -m claude-opus-5

# Resume whatever the wrapped CLI was last doing
ai-gui -p codex-cli --continue

# An HTTP provider running this process's own tools, unattended
ai-gui -p claude --local-tools --yes

# Any provider property, the same names `ai --set` takes
ai-gui -p grok-build --set reasoning-effort=high
#+end_src

Every option is the spelling =ai= and =ai-tui= already use. =--set PROP=VALUE=
in particular needs no work here per provider knob: the preferences dialog
builds its provider page by walking the provider's own writable
=GParamSpec= list, so a property added to a client is reachable from the
command line, from bindings and from this dialog the day it exists.

** Provider and model, per question

Two menus sit under the message box. They choose where the *next*
question goes, and nothing switches while you are using them: the
provider is changed immediately before the message is sent, because a
switch mid-turn would move the conversation out from under a reply that
is still arriving.

The provider list comes off the =AiProviderType= enum, so a provider
added to the library appears without an edit here. The model list is
fetched from the provider itself through
=ai_provider_list_models_async()= and is searchable — a provider can
advertise a hundred models. Three things follow from that:

- A provider that cannot list its models (no key, no CLI installed, no
  network) still offers the one this session is on. The menu degrades;
  it does not empty.
- A model the provider does not advertise — one set with
  =--set model==, say — stays selectable. Dropping it would quietly move
  the next question somewhere else.
- =claude-tmux= implements no listing at all, and asking a provider that
  does not would raise a critical. The interface is checked before the
  call rather than after.

Switching carries context across, exactly as the preferences dialog's
switch does: see [[file:provider-switching.org][provider switching]] and
[[file:native-session.org][native session import]]. While a turn is running the pickers are not
applied — the follow-up is queued against the current provider and the
window says so rather than pretending otherwise.

** The window

Sessions on the left, the conversation on the right, an
=AdwOverlaySplitView= between them that collapses to an overlay below 720px.

| Element | What it is |
|---------+------------|
| Sidebar | Every session, newest first, pinned ones above. Search filters on title, provider and model. |
| Header | The session title, with =provider · model= beneath it. |
| Transcript | A =GtkListView= over the =AiTranscript=, one row per block. |
| Status strip | Activity, elapsed seconds and the queue depth, while a turn is running. |
| Composer | Multi-line input, attachments, completion, and send/stop. |

** Attachments

Click the paperclip, or drop files onto the composer.

An *image* becomes an attachment and is sent as image content. *Anything
else* becomes an =@path= mention in the input line. That split is the
library's, not a simplification: only images have a wire format of their own,
and a text file reaches the model because the harness layer expands the
mention --- which also means the model sees the path it was given rather than
an anonymous blob.

** Search

=Ctrl+F= filters the transcript rather than highlighting inside it, and it
matches against each block *expanded*. A block is the unit the library hands
out and the unit a person reasons about; hiding the ones that do not match
keeps the surviving ones whole, where highlighting a substring inside a
collapsed tool group would point at text the row is not showing. Matching
expanded is what lets somebody find a file name they know was edited without
opening every group first.

** Following

The transcript follows new output only while you are at the bottom. Scroll up
and it stops; scroll back down and it resumes. A streaming transcript that
yanked the reader back down mid-paragraph is the single most annoying thing
this kind of window can do.

** Sessions on disk

Sessions are written to =$XDG_DATA_HOME/ai-glib/gui/sessions/<id>.json=, one
file each, at the end of every turn and again at shutdown. Saving per turn
rather than only at shutdown is the point: a crash mid-session is exactly
when somebody wants the transcript back, and exactly when the shutdown path
does not run.

Three things about what a restored session *is*:

1. *A restored transcript is a record, not a resumption.* The portable
   =AiMessage= history lives inside =AiConversation= and has no setter,
   deliberately. Restored blocks show a person what happened without telling
   the model it happened, and a status line says so rather than leaving it to
   be discovered.
2. *Where the provider keeps its own session, that session is resumed.* The
   provider's =session-id= is saved and set back on reopen, so a wrapped CLI
   brings its own history along --- the mechanism
   [[file:native-session.org][native session import]] already describes. An
   explicit saved id beats =--continue=: they are two answers to "which
   session", and the explicit one is the one somebody clicked on.
3. *The provider is saved by its canonical name*, never
   =ai_provider_get_name()=. That returns a display name ("Claude Code") and
   the factory wants =claude-code=; saving the display name works for the
   providers whose two names coincide and silently stops matching for the
   rest, with the symptom being a session that quietly comes back on the
   default provider.

A file that will not parse costs itself and nothing else. One session
truncated by a crash must not hide the sixteen that survived it --- the same
rule [[file:harness.org][the harness layer]] applies to resource files, and
for the same reason.

** Tool approval

When an HTTP provider runs tools in this process (=--local-tools=), each call
raises a dialog unless =--yes= or the preferences switch is set. The handler
spins a nested =GMainLoop= on =g_main_context_get_thread_default()=, never the
global default: the run it is answering for is driving a private context, and
a loop on the wrong one would never dispatch the source that makes progress.

Approval never fires for the CLI wrappers. They run their own tools in their
own process, which is also why =AiConversation= refuses =local-tools= for
them.

** Background agents

On by default (=--no-agents= opts out), capped at four concurrent. =Ctrl+Shift+G=
shows what is running and offers to stop it.

The panel reports that an agent finished, never what it said. Collecting a
result is =ai_brigade_reap()=, and the model's own =agent_result= tool reaps
too --- whichever asks first gets it, so a panel that displayed results would
be taking them out of the model's hands to satisfy curiosity.

** Building

#+begin_src sh
make gui                # just the client
make                    # everything, including the client when GTK is present
make install            # installs ai-gui and its .desktop file
#+end_src

Fedora packages: =gtk4-devel=, =libadwaita-devel=. On an immutable host these
belong in the image build rather than in a transient overlay.

** The project dashboard

=Ctrl+backslash=, the toolbar's grid button, =/dashboard=, or
=ai-gui --dashboard= at startup. The same key returns to the
conversation with its draft intact; the turn keeps running behind it.

*The registry is shared with ai-tui.* Every ai-glib front-end on this
machine writes the same records under =$XDG_STATE_HOME/ai-glib/sessions=,
so this window lists terminal sessions as well as its own — and can put
one in front of you. See [[file:dashboard.org][the dashboard]] for what a record contains and
how it expires.

Rows are ordered by attention: INPUT, ERROR, WORK, DONE, STOPPED, IDLE,
then DISCONNECTED, and grouped under the project they belong to. That
ordering is reimplemented here to the letter rather than approximated,
because two dashboards reading one registry must not disagree about
which row is first. There is no percentage: a finished model turn does
not prove an issue is resolved.

| Action | What it does |
|--------+--------------|
| Open | This window's own session: switch to it. Anything else: focus its tmux pane |
| Worktree | Branch =ai/<uuid>= into an adjacent =.ai-worktrees/= checkout and open a session there |
| Resume | Start a session on a disconnected record's native provider session, adopting the record |
| Link | Open a linked issue or PR with =xdg-open= |
| Open project… | Start a conversation in another directory |

Four things are deliberate:

1. *Opening a foreign row goes through tmux, and checks first.* A pane
   id is reused when a pane closes, so the pane's published
   =@ai_session= is compared against the record's id before switching.
   Without that check the action opens whatever unrelated work took the
   number.
2. *A new project is a session in this window*, not a new window. ai-tui
   opens a tmux window because it is a terminal program; this keeps every
   conversation one click apart instead of scattered across panes.
3. *Resume adopts the record* rather than starting a second identity
   beside it, so the links and the title already attached survive — and
   it takes the same advisory lock ai-tui does, so two front-ends cannot
   both drive one record.
4. *A worktree is kept whatever happens next.* Uncommitted changes in the
   source checkout are not copied, because =git worktree add= does not
   carry them. Cleanup is Git's usual worktree commands once your work is
   committed.

*** Opening on the dashboard

#+begin_src yaml
apps:
  ai-gui:
    open-dashboard-on-load: true
#+end_src

The default is false, and the preference applies only to a bare launch:
=--continue= or an explicit =--set session-id== means you have already
said which conversation you want. =--dashboard= says it outright;
=--no-dashboard= opts out for one run. This is the same key ai-tui uses
under its own name, and both are read through
=ai_config_get_app_dashboard()=.

** Linked issues and pull requests

#+begin_example
/issue link https://git.example.org/team/project/issues/42
/pr link https://github.com/team/project/pull/81
/links
/issue unlink https://git.example.org/team/project/issues/42
/work https://git.example.org/team/project/issues/42
#+end_example

Linking records an association. It never posts a comment, closes an
issue, or changes a remote assignee. =/work= fetches the title, state and
body and queues *that* as an explicit assignment; a failed fetch submits
nothing, because sending the model "here is your task:" with nothing
after it is worse than saying the fetch did not work.

Links appear as a globe in the header bar whenever the session has any.
Each row reads number, cached remote state, then title — the order
ai-tui uses, so one link reads the same way in both. The state is
cached: a stale =open= sits *beside* the number rather than replacing it.
GitHub metadata needs an authenticated =gh=, Forgejo/Gitea needs =tea=.

** Slash commands

Built-ins resolve in the library and are run here: =/help=, =/commands=,
=/skills=, =/agents=, =/tools=, =/todos=, =/running=, =/kill=, =/clear=,
=/reset=, =/reload=, =/cwd=, =/context=, =/expand=, =/save=, =/export=,
=/links=, =/issue=, =/pr=, =/work=, =/project=, =/dashboard=, =/quit=.

Their output goes into the transcript rather than a toast: =/help= and
=/links= are output, and output that disappears after three seconds is
output somebody has to ask for twice.

=/model=, =/provider= and =/effort= report where the controls are instead
of reimplementing a list you would then have to type an exact id into —
the two menus under the message box and the preferences dialog. =/btw= is
an ai-tui feature; open a second session instead.
