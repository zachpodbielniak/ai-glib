#+TITLE: Steering: words into a running turn

Without steering, a message for a turn that is running waits and becomes
the next turn. Two costs follow. A correction ("stop, use the staging DB")
arrives after the work it was meant to change has finished, and a
follow-up costs a whole extra turn that rereads everything.

=AiSteerable= hands the words to the turn that is running instead, at the
next point the engine itself accepts input: before the next model call,
or at the top of the next round of a tool loop. Nothing is killed,
interrupted or restarted to make room for them.

* The contract: a tri-state

=ai_steerable_steer_finish()= returns one of three answers, and the third
is the one that matters.

| Result                   | Means                                                   | The caller may queue the words again |
|--------------------------+---------------------------------------------------------+--------------------------------------|
| =AI_STEER_REFUSED=       | Provably not delivered. A =GError= says why.            | yes                                  |
| =AI_STEER_DELIVERED=     | The running turn took the words.                        | no                                   |
| =AI_STEER_INDETERMINATE= | Sent, and nothing confirmed it: a wait ran out, or the  | no                                   |
|                          | run ended while the answer was in flight.               |                                      |

=AI_STEER_INDETERMINATE= counts as delivered. The words may already be
running, and running them twice is the one mistake steering must never
make. Every implementation keeps the same rule: a steer is =REFUSED= only
while not one byte of it has reached the engine.

=AI_STEER_REFUSED= is zero, so a zero-initialised result never reads as a
delivery.

** Refusals

Every =AI_STEER_ERROR= code means the words were *not* delivered.

| Code                             | When                                                         |
|----------------------------------+--------------------------------------------------------------|
| =AI_STEER_ERROR_NOT_SUPPORTED=   | the class cannot steer (=can_steer= is %FALSE)               |
| =AI_STEER_ERROR_NO_ACTIVE_TURN=  | no turn is running, or it ended before the words were sent   |
| =AI_STEER_ERROR_TURN_MISMATCH=   | the turn id the caller held is not the one running           |
| =AI_STEER_ERROR_AMBIGUOUS=       | no turn id was given and more than one turn is running       |
| =AI_STEER_ERROR_NOT_STEERABLE=   | a turn is running but cannot take input now                  |
| =AI_STEER_ERROR_SEND_FAILED=     | the words could not be sent at all                           |
| =AI_STEER_ERROR_CANCELLED=       | the caller cancelled before anything was sent                |

* The API

#+begin_src C
/* Can this kind of client steer at all?  A class datum: ask a probe. */
gboolean       ai_steerable_can_steer   (AiSteerable *self);

/* The turn running now, as a handle to hold; NULL when none. */
gchar         *ai_steerable_dup_turn_id (AiSteerable *self);

void           ai_steerable_steer_async  (AiSteerable *self,
                                          const gchar *turn_id,   /* nullable */
                                          const gchar *text,
                                          GCancellable *cancellable,
                                          GAsyncReadyCallback callback,
                                          gpointer user_data);
AiSteerResult  ai_steerable_steer_finish (AiSteerable *self,
                                          GAsyncResult *result,
                                          GError **error);

const gchar   *ai_steer_result_to_string (AiSteerResult result);
          /* "refused" | "delivered" | "indeterminate" */
#+end_src

** Asking a probe client

Whether a class can steer is =AiSteerableInterface.can_steer=, a class
datum like =AiCliClientClass.config_dir_env=. Every client implements the
interface -- each CLI wrapper through =AiCliClient=, each HTTP client
through =AiClient= -- so a caller never keeps a table of providers.

One class answers per instance: =AiCodexCliClient= can steer only on its
=app-server= transport, so it sets =can_steer= %TRUE *and* the optional
=AiSteerableInterface.is_steerable= vfunc, and =ai_steerable_can_steer()=
asks the instance. A probe for codex must therefore be configured the way
the real client will be (=transport= set). Every other class leaves
=is_steerable= %NULL and answers for the class as before:

#+begin_src C
if (AI_IS_STEERABLE (client) &&
    ai_steerable_can_steer (AI_STEERABLE (client)))
  ai_steerable_steer_async (AI_STEERABLE (client), NULL, text,
                            NULL, on_steered, self);
else
  queue_for_next_turn (self, text);
#+end_src

A class with =can_steer= %FALSE answers every steer with =REFUSED= and
=AI_STEER_ERROR_NOT_SUPPORTED= without its vfuncs being called, so
implementing the interface with %FALSE is the whole job for a class that
cannot steer. The same holds for an instance whose =is_steerable= says
no (a codex client on =exec=).

** The turn handle

A steer targets a *running* turn. =ai_steerable_dup_turn_id()= names the
one running now (the newest, if several are). The id is opaque and local
to this process; it is not the engine's own turn id.

Passing it back to =ai_steerable_steer_async()= makes the steer land in
that turn or nowhere: if a different turn is running by then the answer
is =REFUSED= with =AI_STEER_ERROR_TURN_MISMATCH=, never a delivery into
the next turn. With =turn_id= %NULL the steer goes to whichever turn is
running, and is refused as =AMBIGUOUS= when there is more than one.

For a CLI client the id appears when the stream run starts -- inside
=ai_streamable_chat_stream_async()=, before it returns -- and disappears
when the run ends. For =AiToolExecutor= it appears when a run starts and
disappears when it finishes.

** Threads and cancellation

=ai_steerable_steer_async()= may be called from any thread; the callback
runs in the caller's thread-default main context. A steer for a stream
running on a worker thread's private context -- libreclaw's shape -- hops
onto that context to write, and the answer hops back.

The cancellable is honoured only until the words are sent. After that a
cancel cannot take them back, so the answer is whatever the engine says,
and a steer cancelled late is never reported as a refusal.

* Per engine

| Client                | =can_steer= | Seam                                                       | Verified                     |
|-----------------------+-------------+------------------------------------------------------------+------------------------------|
| =AiClaudeCodeClient=  | TRUE        | a stream-json user event on the open stdin                 | claude 2.1.325, control run  |
| =AiClaudeTmuxClient=  | TRUE        | a line typed into the TUI while it works                   | claude 2.1.325, control run  |
| =AiToolExecutor=      | TRUE        | parked, spliced in at the top of the next round            | tests                        |
| =AiCodexCliClient=    | per         | =turn/steer= on =codex app-server= (=transport=            | protocol source and a fake   |
|                       | transport   | =app-server=); exec: FALSE                                 | server only -- see below     |
| opencode, grok-build, | FALSE       | none: queue only                                           | --                           |
| antigravity, cursor   |             |                                                            |                              |
| HTTP clients          | FALSE       | none on the client; steer the =AiToolExecutor= running it  | --                           |

** Claude Code

Steering is opt-in per client: set =AiClaudeCodeClient:steerable= to
%TRUE. With it on, a *streamed* turn (=ai_streamable_chat_stream_async()=)
runs

#+begin_example
claude --print --input-format stream-json --output-format stream-json \
       --verbose --replay-user-messages ...
#+end_example

and writes the prompt as one JSON user event carrying a fresh ="uuid"=.
stdin then stays open. A steer writes another user event with its own
uuid. Claude takes it before its next model call and, because of
=--replay-user-messages=, echoes it back on stdout with that uuid
(="isReplay": true=) at the moment it takes it.

| What happened                                         | Result          |
|-------------------------------------------------------+-----------------|
| the echo with the steer's uuid arrived                | =DELIVERED=     |
| written, and the run ended with no echo               | =INDETERMINATE= |
| a write error before any byte of it went in           | =REFUSED=       |
| part of it written, then a write error                | =INDETERMINATE= |
| the =result= line had already arrived                 | =REFUSED=       |

The =result= line ends the turn: stdin closes as soon as no steer is
still being written or waiting for its echo, and claude exits. A steer
written but not yet echoed when =result= arrives is run by claude as a
follow-on turn in the same process; stdin closes once its echo arrives,
and the reader carries on to the follow-on turn's =result=. Echoes are
never treated as model output.

With =steerable= off (the default) a streamed turn is exactly what it was
before -- the prompt as text on stdin, closed at once -- and a steer is
refused with =AI_STEER_ERROR_NOT_STEERABLE=. It is opt-in because an open
stdin changes what the child sees: a stand-in for claude that reads stdin
to EOF before answering (the usual test double, ai-glib's own included)
would wait forever. The class datum stays %TRUE: the class *can* steer.

The one-shot paths (=ai_provider_chat_async()=, =ai_cli_client_chat_sync()=)
close stdin with the prompt as before, so they have no turn to steer: a
steer during one is refused as =NO_ACTIVE_TURN=.

*** How this was verified

=--help= is not the whole flag list (=--system-prompt-file= taught us
that), so the flags were checked with a control experiment against the
installed claude 2.1.325, using haiku and a turn that runs =sleep 12=:

- Control: a prompt written as a stream-json user event, stdin left
  open. One =result=; the process stays alive until stdin closes, then
  exits.
- Steer: a second user event written six seconds in, while the tool ran.
  claude echoed it (=isReplay=) after the tool result and before the next
  model call; one =result=, whose text obeyed the steered instruction.
- Late: a user event written *after* =result=, stdin closed straight
  after. claude ran it as a second turn with its own =result=, and echoed
  the caller's uuid back unchanged.

The same steer then ran end to end through =AiClaudeCodeClient=: steered
when the tool started, answered =DELIVERED= when the echo came after the
twelve-second tool, reply obeying it.

** Claude Code in tmux

=AiClaudeTmuxClient= drives the interactive TUI, and typing into the TUI
while it works queues the line in Claude Code itself. A steer is a
bracketed paste of a prompt file and an Enter, while the turn is busy --
from the moment the turn's own prompt was accepted until the turn is
judged over.

The answer is read back the way the turn's own prompt is, from the
transcript, and from the pane when the transcript cannot say:

| What happened                                                  | Result          |
|----------------------------------------------------------------+-----------------|
| a =queue-operation= =enqueue= appeared in the transcript       | =DELIVERED=     |
| the paste failed (the draft is then cleared)                   | =REFUSED=       |
| after every Enter the line still sits in the draft box;        | =REFUSED=       |
| it is cleared with =C-u= and was never submitted               |                 |
| neither queued nor in the draft box                            | =INDETERMINATE= |

claude logs the hand-over too: a =queue-operation= =remove= with reason
=absorbed_mid_turn= when the running turn takes the line. That is what
makes the end of a turn safe. When the Stop hook fires, the turn counts
=enqueue= against =remove= / =dequeue= past its watermark; while a steered
line is still queued, claude will run it the moment it stops, so the
turn removes the sentinel and waits for the next Stop instead of killing
the session. The decision is made under the same lock a steer holds for
its whole length, so a steer cannot be typed between the reading and the
closing.

Verified against claude 2.1.325 in tmux the same way: a line pasted
during =sleep 15= was logged =enqueue= at once and =remove=
(=absorbed_mid_turn=) eleven seconds later, the pane showing "Press up
to edit queued messages" in between; one Stop, the reply obeying the
line. Through =AiClaudeTmuxClient= the steer answered =DELIVERED= within
a second and the reply obeyed it.

** ai-glib's own tool loop

=AiToolExecutor= is itself an =AiSteerable=, and always can steer. This
is how the HTTP providers -- whose clients cannot -- get steering at all:
steer the executor running them.

The words are parked on the run and spliced in at the *top of the next
round*, as one user message after every tool result of the batch that
just ran -- never between two of them, which would separate a tool call
from its result -- and before the next request. The brigade's "background
agent finished" notice is the other producer feeding the same splice;
when both are pending they go in as one message, notice first.

| What happened                                            | Result      |
|----------------------------------------------------------+-------------|
| spliced into the conversation                            | =DELIVERED= |
| the run ended first (final answer at the turn limit, an  | =REFUSED=   |
| error, a cancel)                                         |             |
| no run in progress                                       | =REFUSED=   |

A steer that arrives while the model writes what would have been its
final answer makes that answer not final: the run goes round once more
with the words, bounded by the turn limit like everything else.

The answer comes at the splice, not when the words are parked, because
until then the run might still end without them -- and then they are
provably undelivered.

When the executor runs a provider that can steer itself and a request is
in flight, the words go straight into that request instead (a streamed
claude-code turn under the executor); if the provider refuses, they are
parked for the next round as usual.

** Everything else

Every other client says =can_steer= %FALSE. For ACP-style engines
(opencode, grok-build, antigravity, cursor) that is the protocol, not an
omission: a turn accepts no input but a cancel, and interrupting and
re-prompting to fake a seam would break the "nothing is killed" rule.
The caller queues the words for the next turn, as it always has.

** Codex (=codex app-server=)

=AiCodexCliClient= has two transports, chosen by its =transport= property:

- =exec= (the default, unchanged): =codex exec --json=. No input reaches a
  running turn, so =ai_steerable_can_steer()= is %FALSE and a steer is
  refused with =AI_STEER_ERROR_NOT_SUPPORTED=.
- =app-server=: =codex app-server=, JSON-RPC over stdio, one process per
  turn. =ai_steerable_can_steer()= is %TRUE and a steer is a =turn/steer=
  request naming the running turn.

*** The conversation

#+begin_example
-> {"id":1,"method":"initialize","params":{"clientInfo":{"name":"ai-glib",...}}}
<- {"id":1,"result":{...}}
-> {"method":"initialized"}
-> {"id":2,"method":"thread/start","params":{"model":..,"cwd":..,
       "approvalPolicy":"never","sandbox":"read-only","ephemeral":true}}
     (or "thread/resume" with "threadId" when the client has a session id)
<- {"id":2,"result":{"thread":{"id":"thr-..."},...}}
-> {"id":3,"method":"turn/start","params":{"threadId":"thr-...",
       "input":[{"type":"text","text":<prompt>},{"type":"localImage",...}],
       "effort":..}}
<- {"id":3,"result":{"turn":{"id":"turn-..."}}}
<- turn/started, item/started, item/agentMessage/delta, item/completed,
   thread/tokenUsage/updated, ...
<- {"method":"turn/completed","params":{"turn":{"status":"completed",..}}}
-> EOF on stdin; app-server exits
#+end_example

The request ids are fixed (1, 2, 3, then 4 onwards for steers), and the
turn id a steer names is codex's own, taken from the =turn/start= answer
or =turn/started=, whichever comes first.

*** A steer

#+begin_example
-> {"id":4,"method":"turn/steer","params":{"threadId":"thr-...",
       "expectedTurnId":"turn-...","input":[{"type":"text","text":..}]}}
#+end_example

| What happened                                                   | Result          |
|-----------------------------------------------------------------+-----------------|
| a =result= (={"turnId":..}=)                                    | =DELIVERED=     |
| error "no active turn to steer" (=NoActiveTurn=, and the other  | =REFUSED=,      |
| reasons codex folds into it)                                    | =NO_ACTIVE_TURN= |
| error "expected active turn id `x` but found `y`"               | =REFUSED=,      |
| (=ExpectedTurnMismatch=)                                        | =TURN_MISMATCH= |
| any other error from validation (-32600: a review or compact    | =REFUSED=,      |
| turn, empty input, a draining server; -32601 from an older      | =NOT_STEERABLE= |
| app-server without =turn/steer=)                                |                 |
| internal error (-32603, "failed to steer turn: ...")            | =INDETERMINATE= |
| written, and no answer within =steer-timeout-ms= (10 s)         | =INDETERMINATE= |
| written, and the run ended before the answer                    | =INDETERMINATE= |
| before codex named its turn (handshake still running)           | =REFUSED=,      |
|                                                                 | =NOT_STEERABLE= |
| after =turn/completed=                                          | =REFUSED=,      |
|                                                                 | =NO_ACTIVE_TURN= |

A =REFUSED= after the request went out is still provably not delivered:
in =turn_processor.rs= every error path returns before, or instead of,
submitting the input; success is answered only for
=SteerSubmission::Steered=. The internal error is the exception, because
it comes from the core call itself, so it is =INDETERMINATE=.

*** Everything else the transport does

- *Text streams.* =item/agentMessage/delta= becomes =AI_EVENT_TEXT_DELTA=
  as it arrives (exec only has whole messages); the completed item adds
  the full text to the response without repeating the deltas. Reasoning
  deltas become =AI_EVENT_THINKING_DELTA=.
- *Tools* keep exec's names (=command_execution=, =file_change=,
  =mcp_tool_call=, =web_search=, plus =dynamic_tool_call=), so the view
  layer styles both transports alike. The tool input is the
  =ThreadItem= as codex sent it (camelCase keys).
- *Usage* is the sum of the turn's =thread/tokenUsage/updated= =last=
  figures, priced as exec's.
- *Failure* is =turn/completed= with status =failed= (or =interrupted=).
  The =TurnError= message goes through the same phrase table as exec's
  =turn.failed=, so a usage limit is =AI_ERROR_SESSION_LIMIT= with the
  same notice; when the words match nothing but =codexErrorInfo= says
  =usageLimitExceeded=, =rateLimitExceeded=, =unauthorized= or a retry
  limit on HTTP 429, that decides. A refused =thread/start= or
  =turn/start= fails the run with codex's words.
- *Approvals* are answered as exec's flags decide them. The thread runs
  with =approvalPolicy= =never= (exec's =--ask-for-approval never=), so
  codex should not ask; if it does, a command or file change is
  =decline=d (=denied= on the legacy methods), or =accept=ed
  (=approved=) under =skip-permissions=, whose thread also runs
  =danger-full-access= (exec's bypass flag). Extra permissions are never
  granted; an MCP elicitation is declined; any other server request
  (user input, dynamic tools, token refresh, attestation) gets a
  JSON-RPC error so codex never waits on it. Each answered approval is
  also an =AI_EVENT_STATUS=.
- *Configuration* without a request field goes in root =-c= overrides
  before =app-server=: granted MCP servers, =web_search="live"= for
  =search=, and =sandbox_workspace_write.writable_roots= for
  =additional-directories= (made absolute against the working
  directory). =profile= is refused before launch, because codex rejects
  =--profile= for app-server.
- *Resume* is =thread/resume= by session id. =continue-session= without a
  session id has no app-server form (exec's =resume --last=) and starts a
  new thread.
- *Every entry point* runs the protocol: =ai_streamable_chat_stream_async()=,
  =ai_provider_chat_async()=, and =ai_cli_client_chat_sync()= (on a
  private main context). All three are steerable, unlike claude-code,
  whose one-shot paths close stdin with the prompt.

* For a CLI wrapper: implementing a seam

The shared stream reader in =AiCliClient= does the plumbing. Re-implement
=AiSteerable= in the subclass with =can_steer= %TRUE and, per instance,
call =ai_cli_steer_set_open_input()= (claude-code does it from its
=steerable= property, codex from its =transport=); from then on =ai_cli_client_stream_run_async()=
keeps that client's stdin open: the
prompt goes in first, behind it whatever is steered, and the pipe
belongs to an =AiCliSteerChannel= (=src/core/ai-cli-steer-private.h=).

The subclass supplies three things:

1. =steer_async= calling =ai_cli_steer_async()= with a builder that turns
   the words into the bytes the CLI reads, and optionally an
   acknowledgement key the CLI will echo back.
2. In =parse_stream_events=, =ai_cli_steer_channel_resolve()= when the
   CLI acknowledges a key -- the channel of the line being parsed is
   =ai_cli_steer_current()=.
3. In =parse_stream_events=, =ai_cli_steer_channel_settle()= when the CLI
   says the turn is over. *This is mandatory*: it is what closes stdin,
   and a CLI waiting for EOF never exits without it. The process
   deadline (=process-timeout-ms=) is the only backstop.

A protocol that needs more than one write -- codex's JSON-RPC handshake
-- writes its own lines with =ai_cli_steer_channel_write()= from the
parser, and keeps per-run state on the channel
(=ai_cli_steer_channel_set_data()=), so the handshake and the steers
share one ordered pipe. A class whose instances differ in whether they
can steer sets =is_steerable= next to =can_steer= %TRUE.

The channel keeps the tri-state rule for every implementation: queued
and not started is =REFUSED= at settle or run end; on the wire or
awaiting an acknowledgement when the run ends is =INDETERMINATE=.

Writing into a pipe the child has just closed raises =SIGPIPE=, whose
default action kills the caller. The first steerable channel sets
=SIGPIPE= to ignored if, and only if, nobody installed a handler --
=ai-mcp-host.c= already does the same.

* For libreclaw

A message for an =LcSession= whose turn is running, with =steer: true=:

#+begin_src C
if (AI_IS_STEERABLE (client) &&
    ai_steerable_can_steer (AI_STEERABLE (client)))
  ai_steerable_steer_async (AI_STEERABLE (client), turn_id, text,
                            NULL, on_steered, message);
else
  g_queue_push_tail (&self->pending, message);

static void
on_steered (GObject *source, GAsyncResult *result, gpointer user_data)
{
  g_autoptr(GError) error = NULL;
  AiSteerResult outcome =
      ai_steerable_steer_finish (AI_STEERABLE (source), result, &error);

  if (outcome == AI_STEER_REFUSED)
    push_onto_the_queue (user_data);         /* as today */
  else
    record_once_as_steered (user_data,        /* DELIVERED or INDETERMINATE */
                            ai_steer_result_to_string (outcome));
}
#+end_src

- Set =steerable= on the =AiClaudeCodeClient= when the session is built.
- For codex, set =transport= to ="app-server"= on the =AiCodexCliClient=
  (=g_object_set (client, "transport", "app-server", NULL)= or
  =ai_codex_cli_client_set_transport (client,
  AI_CODEX_CLI_TRANSPORT_APP_SERVER)=) when the session is built; that
  alone makes =ai_steerable_can_steer()= %TRUE. Keep
  =session-persistence= on and =session-id= set as today: the thread id
  is resumed with =thread/resume=. Do not set =profile= (refused on
  app-server). Optionally tune =steer-timeout-ms= (default 10000).
  Unverified against a real codex until
  =examples/steer-codex-app-server= has passed (see above).
- Only a *streamed* claude-code turn is steerable. A session that runs
  its turns through =ai_cli_client_chat_sync()= has nothing to steer; it
  must take the =AiStreamable= path for any session that may be steered.
  (codex on app-server is steerable on every path.)
- =turn_id= is =ai_steerable_dup_turn_id()= taken when the turn started;
  =NULL= is fine when the session runs one turn at a time.
- Call from the main thread; the stream on the worker thread's private
  context is reached safely, and the callback comes back to the caller.
