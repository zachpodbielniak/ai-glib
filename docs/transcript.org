* The transcript: a conversation you can render
ai-glib models a conversation as an ordered list of *blocks* --- a user
turn, a paragraph of assistant prose, a group of tool calls, a token count
--- and hands a frontend each one as text plus styled spans. Deciding that
five tool calls read as =Edited 3 files, ran 2 commands  +21-6= happens
once, in the library. An ncurses harness and an Emacs buffer both consume
the result and neither of them knows what a tool is.

That split is the whole design. This document is about where the line falls
and how to sit on either side of it.

#+begin_example
  providers ──emit AiEvent──▶ AiConversation ──folds into──▶ AiTranscript
  (AiEventSource)             (the driver)                   (GListModel<AiViewBlock>)
                                                                     │
                                               ai_view_block_render(block, width)
                                                                     │
                                                     AiRenderedText { text, spans }
                                                         ╱                    ╲
                                             ncurses attr_t          Emacs text properties
#+end_example

** The shortest useful program
#+begin_src C
g_autoptr(AiClaudeClient) client = ai_claude_client_new ();
g_autoptr(AiConversation) conversation = ai_conversation_new (G_OBJECT (client));

g_signal_connect (ai_conversation_get_transcript (conversation),
                  "items-changed", G_CALLBACK (on_items_changed), self);

ai_conversation_send_async (conversation, "what changed in HEAD?",
                            NULL, on_sent, loop);
#+end_src

Everything after that is rendering. =examples/transcript-render.c= is a
complete frontend in a hundred lines, most of them a switch mapping style
roles to ANSI colours; read it before writing your own.

** The transcript survives a provider switch
=ai_conversation_set_provider()= changes who handles the next turn without
replacing the =AiTranscript=. Existing block ids, expanded state and rendered
history remain valid, so an attached frontend keeps watching the same object.
There is no detach/rebuild cycle.

The transcript is not replayed to the new model. =AiConversation='s
provider-neutral =AiMessage= history is the canonical context; rendered
markers, wrapping and status blocks are presentation. Completed tool calls
and results survive in the message content blocks even if their transcript
group is collapsed.

A switch is refused while =busy=, which also guarantees that an open
streaming block cannot change owners halfway through. CLI targets start a
fresh native session and receive a text projection of the message history;
provider-owned JSONL and session stores are not imported.

See [[file:provider-switching.org][Provider switching]] for the complete
migration and failure rules.

** Blocks
| Kind                     | Type                  | Carries                          |
|--------------------------+-----------------------+----------------------------------|
| =AI_VIEW_BLOCK_TURN=     | =AiViewTurnBlock=     | what the user said               |
| =AI_VIEW_BLOCK_TEXT=     | =AiViewTextBlock=     | assistant prose, grown by deltas |
| =AI_VIEW_BLOCK_THINKING= | =AiViewThinkingBlock= | reasoning, collapsed by default  |
| =AI_VIEW_BLOCK_TOOL=     | =AiViewToolBlock=     | a group of calls, summarised     |
| =AI_VIEW_BLOCK_STATUS=   | =AiViewStatusBlock=   | a note, token counts, a failure  |

Every block answers =ai_view_block_get_id()= with a number unique for the
life of the process. *Key your frontend's map on that, not on the position.*
Positions shift when blocks are removed; ids do not.

Two flags live on the base class because a frontend should be able to offer
the same affordance everywhere without asking what it is looking at:
=expanded= (the =›= / =⌄= marker) and =complete= (whether the block is still
being streamed into, which is what a spinner keys on).

** The rhythm, and where it comes from
A session reads as narration, a collapsed tool group, more narration. That
is not something the frontend arranges --- it falls out of three rules in
=AiConversation='s folding:

- A =AI_EVENT_TEXT_DELTA= appends to the open prose block, opening one if
  there is none.
- A =AI_EVENT_TOOL_STARTED= joins the open tool group, opening one if there
  is none. *That is the grouping.*
- Anything else closes what is open, so the next delta after a tool group
  starts a *new* paragraph rather than continuing the one before it.

Without that last rule the narration before and after a tool group would run
together into one paragraph with the group wedged in the middle of it.

** The render contract
#+begin_src C
AiRenderedText *rendered = ai_view_block_render (block, width);

const gchar *text = ai_rendered_text_get_text (rendered);

for (i = 0; i < ai_rendered_text_get_n_spans (rendered); i++)
{
    guint start, len;
    AiStyleTag tag;

    ai_rendered_text_get_span (rendered, i, &start, &len, &tag);
    /* text[start .. start+len) should look like `tag` */
}
#+end_src

Three things about that are load-bearing.

*** Offsets are byte offsets into UTF-8
Which is what C, =fwrite()= and ncurses all want. Emacs counts characters,
and converts with =byte-to-position=; the recipe below does exactly that. A
span never begins or ends inside a multi-byte sequence, so the conversion is
always well defined. Spans are sorted by =start=, never overlap, and are
never empty.

*** Width is measured in terminal columns
Not characters. A CJK ideograph is one character and two columns, and a
renderer that counted characters would misalign every line containing one.
=ai_style_text_width()= is the same measure the wrapper uses.

Pass =width = 0= to mean *do not wrap*. That is the right answer for Emacs,
which fills text itself and would fight with pre-wrapped content. A terminal
passes its column count and gets lines that fit.

*** Tags are roles, not colours
=AI_STYLE_ADDED= says "this run is an addition". Whether that is green,
bold, or underlined is the frontend's decision and the library has no
opinion. =ai_style_tag_to_string()= gives each role a stable name ---
="tool-name"=, ="added"= --- which is what makes a mapping table one lookup.

| Tag                     | Means                                     |
|-------------------------+-------------------------------------------|
| =AI_STYLE_USER_PROMPT=  | something the user typed                  |
| =AI_STYLE_TOOL_NAME=    | the verb of a group --- "Edited", "Ran"   |
| =AI_STYLE_TOOL_TARGET=  | what it acted on --- a file or a command  |
| =AI_STYLE_TOOL_OK= / =_FAILED= / =_PENDING= | a call's outcome      |
| =AI_STYLE_ADDED= / =_REMOVED= | the =+21= and the =-6=              |
| =AI_STYLE_THINKING=     | reasoning, which is not the answer        |
| =AI_STYLE_MARKER=       | the expand/collapse affordance            |
| =AI_STYLE_CODE= / =_DIM= / =_ERROR= / =_STATUS= / =_LINK= / =_HEADING= | as they read |

Renderings are cached against =(width, revision)=, so asking repeatedly at
one width is cheap and asking after a mutation is correct. A terminal resize
re-renders; it does not re-derive.

** Tool groups
=AiViewToolBlock= is where the summarising lives. Collapsed it is one line;
expanded it is one line per call. The wording comes out of the
=AiToolStyle= table:

1. Bucket the calls by category, *in the order the categories were first
   used* --- the summary reads as a sequence of what happened.
2. One call in a bucket with a known target names it: =Edited ai-style.c=.
   Several become a count: =Edited 3 files=.
3. Join with commas, lowercasing every clause after the first.
4. Append the aggregate =+21-6=, from the calls whose style says
   =counts_diff=. Omitted entirely when nothing changed --- a group that
   only ran commands carries no diff figure.
5. Append the marker, and a =(2 failed)= clause if anything failed.

The diff figures are derived from the *request*, not the result: an edit
replaces one exact string with another, so the line counts of the two are
the answer. A tool whose style does not claim =counts_diff= contributes
nothing, which is why running a command never inflates the total.

*** Teaching it a new tool
One struct literal, the same way =AiImageModelInfo= registers an image
model:

#+begin_src C
const AiToolStyle style = {
    "deploy",                    /* the name the model uses      */
    "Deployed",                  /* past tense, capitalised      */
    "service", "services",       /* singular, plural             */
    AI_TOOL_CATEGORY_COMMAND,    /* which bucket it groups into  */
    "target",                    /* input naming what it acted on */
    FALSE                        /* contributes to +N-M?          */
};

ai_tool_style_register (&style);
#+end_src

The built-in table already covers ai-glib's own lowercase tools (=bash=,
=edit=, =write=, ...) and the capitalised ones the wrapped CLIs use (=Bash=,
=Edit=, =Write=, =Task=, ...), because both end up in the same transcript.
Matching is case-sensitive on purpose: =edit= is ours and =Edit= is
claude-code's, and although they read alike today they need not.

An unregistered tool still renders, under a generic verb for its category
(=Used 1 tool=). A transcript that silently omitted a call would be lying
about what ran.

** Observing changes
=AiTranscript= is a =GListModel=, so =::items-changed= reports insertions
and removals in the form every GLib consumer already knows.

That is not enough on its own. A block being *streamed into* is neither an
insertion nor a removal --- prose grows a delta at a time, a tool group's
calls change state --- so a frontend watching only =items-changed= would
show the first delta of a reply and nothing after it. Hence:

#+begin_src C
void block_changed (AiTranscript *t, guint position, AiViewBlock *block, gpointer data);
#+end_src

Update that one region rather than redrawing everything. And *coalesce*: a
streamed reply fires this per token, and redrawing on each would spend the
whole turn in refresh. =ai-tui= schedules one redraw per main-loop iteration
with =g_idle_add()=, which is indistinguishable to a reader.

** Rendering into Emacs
This is the reason the layer exists, so here it is in full. Everything below
goes through GObject Introspection; =make test-gi= exercises the same calls
from Python precisely so that this keeps working.

#+begin_src emacs-lisp
;;; ai-glib-transcript.el --- render an AiTranscript into a buffer -*- lexical-binding: t; -*-

(require 'gi)
(gi-require-namespace "AiGlib" "1.0")

(defface ai-glib-face-tool-name   '((t :inherit font-lock-keyword-face))   "")
(defface ai-glib-face-tool-target '((t :inherit font-lock-string-face))    "")
(defface ai-glib-face-added       '((t :foreground "green"))               "")
(defface ai-glib-face-removed     '((t :foreground "red"))                 "")
(defface ai-glib-face-thinking    '((t :inherit shadow :slant italic))     "")
(defface ai-glib-face-marker      '((t :inherit shadow))                   "")
;; ... one per ai_style_tag_to_string() name.

(defvar-local ai-glib--regions (make-hash-table)
  "Block id -> (start-marker . end-marker).")

(defun ai-glib--face-for (tag)
  "The face for style role TAG, or nil when there is none."
  (let ((sym (intern (format "ai-glib-face-%s" (AiGlib-style-tag-to-string tag)))))
    (and (facep sym) sym)))

(defun ai-glib--insert-block (block)
  "Insert BLOCK at point, applying its spans as text properties."
  ;; Width 0: Emacs fills text itself, so pre-wrapped content would fight it.
  (let* ((rendered (AiGlib-view-block-render block 0))
         (text     (AiGlib-rendered-text-get-text rendered))
         (origin   (point)))
    (insert text)
    (dotimes (i (AiGlib-rendered-text-get-n-spans rendered))
      (pcase-let ((`(,ok ,start ,len ,tag)
                   (AiGlib-rendered-text-get-span rendered i)))
        (when ok
          ;; Spans are BYTE offsets into UTF-8; Emacs wants character
          ;; positions. byte-to-position converts, and a span never begins
          ;; or ends inside a character, so this is always exact.
          (let ((beg (byte-to-position (+ (position-bytes origin) start)))
                (end (byte-to-position (+ (position-bytes origin) start len)))
                (face (ai-glib--face-for tag)))
            (when face
              (put-text-property beg end 'face face))))))
    (insert "\n\n")
    (puthash (AiGlib-view-block-get-id block)
             (cons (copy-marker origin) (copy-marker (point) t))
             ai-glib--regions)))

(defun ai-glib--replace-block (block)
  "Re-render BLOCK in place, for a block that grew."
  (let ((region (gethash (AiGlib-view-block-get-id block) ai-glib--regions)))
    (if (null region)
        (ai-glib--insert-block block)
      (save-excursion
        (delete-region (car region) (cdr region))
        (goto-char (car region))
        (ai-glib--insert-block block)))))

(defun ai-glib-attach (conversation buffer)
  "Mirror CONVERSATION's transcript into BUFFER."
  (with-current-buffer buffer
    (let ((transcript (AiGlib-conversation-get-transcript conversation)))
      ;; Insertions and removals.
      (gi-signal-connect
       transcript "items-changed"
       (lambda (model position _removed added)
         (with-current-buffer buffer
           (let ((inhibit-read-only t))
             (save-excursion
               (goto-char (point-max))
               (dotimes (i added)
                 (ai-glib--insert-block
                  (g-list-model-get-item model (+ position i)))))))))

      ;; Streaming, which items-changed does not cover.
      (gi-signal-connect
       transcript "block-changed"
       (lambda (_t _position block)
         (with-current-buffer buffer
           (let ((inhibit-read-only t))
             (ai-glib--replace-block block))))))))
#+end_src

Two things worth repeating, because they are the only places a frontend can
get this wrong:

- =byte-to-position= is not optional. Span offsets are bytes; a buffer
  containing one accented filename would misplace every face after it
  otherwise.
- =::block-changed= is not optional either. Without it the buffer shows the
  first delta of each reply and then stops.

The =›= marker is a span like any other, so binding a key to
=AiGlib-view-block-set-expanded= on the block under point gives you
collapse/expand with no further work.

** Exporting a session
=ai_transcript_export()= writes the whole transcript as a document:

#+begin_src C
g_autofree gchar *doc = ai_transcript_export(transcript,
                                             AI_EXPORT_FORMAT_ORG);
#+end_src

| Format                       | Name         | Extension | Folds with        |
|------------------------------+--------------+-----------+-------------------|
| =AI_EXPORT_FORMAT_TEXT=      | ="text"=     | =txt=     | ---               |
| =AI_EXPORT_FORMAT_MARKDOWN=  | ="markdown"= | =md=      | =<details>=       |
| =AI_EXPORT_FORMAT_ORG=       | ="org"=      | =org=     | an outline heading |

=AI_EXPORT_FORMAT_TEXT= is exactly =ai_transcript_to_text (t, 0)=, so a
frontend has one entry point rather than a special case for the format it
started with. =ai_export_format_from_string()= parses a name
case-insensitively and accepts ="md"= and ="org-mode"=; it returns =FALSE=
on anything else rather than defaulting, so =/export mardkown= says so
instead of quietly writing the wrong format.

Three decisions in here are worth knowing, because each is a way an
exporter can be subtly wrong:

- *Blocks export expanded, whatever the display shows.*
  =ai_view_block_render_expanded()= renders a block as though its expand
  flag were set, without setting it and without emitting
  =::block-changed=. A collapsed tool group renders as one summary line,
  and a file that recorded "Edited 3 files" without saying which is not a
  record of anything --- while an exporter that flipped the flag instead
  would make every attached frontend redraw because somebody saved a file.
- *The rendering is not the content.* A turn renders with a leading
  ="> "=, a thinking block with ="✳ thinking ⌄"=. Those orient a reader on
  a screen; in a file the heading above already says which is which, and
  in org ="> "= is not syntax at all. So the four text-bearing kinds are
  read through their own getters, and only tool, todo and agent blocks ---
  whose markers *are* the information --- go through the renderer.
- *Prose is passed through; output is fenced.* Models already write
  markdown, so escaping assistant prose would ruin every code fence in the
  answer. Tool output is the opposite: it is whatever a command printed,
  and a diff line beginning with =#= must not become a heading.

The =/export= built-in carries the same thing to a user:
=/export org ~/notes/session.org=. The path is optional --- the format
already implies an extension.

** Testing a frontend
=ai_transcript_to_text (transcript, width)= renders the whole thing as plain
text, which is what =ai-tui --dump= prints and what
=tests/test-ai-tui.c= asserts against. It is the cheapest way to check that
a session produced what you expected without driving a display.

* The todo block
=AiViewTodoBlock= is the sixth block kind, and the only one that mutates
in place.

#+begin_example
  ☐ Add the parser
  ◐ Wiring the registry
  ☑ Read the files
  1/3 done
#+end_example

=AiConversation= watches the executor's =::todos-changed= and keeps one
block, updating it rather than appending. A model revises its plan
repeatedly over a long task, and eight appended copies of a nine-line
list is not a transcript anybody can read.

An update therefore emits =::block-changed=, not =::items-changed= ---
which is exactly why a frontend has to watch both. An empty list gets no
block at all.

The in-progress item renders in its active phrasing ("Wiring the
registry"), because a list is read while it is being worked on. That rule
lives in =ai_todo_get_label()=, once, rather than in every renderer.

Each line carries a =todo-pending=, =todo-active= or =todo-done= span, so
a frontend colours them without parsing the glyphs back out of the text.

* The background-agent block
=AiViewAgentBlock= is the seventh block kind, and follows the todo
block's rule for the same reason: an agent changes state several times
over its life, and a transcript that grew a block per change would bury
the conversation the panel belongs to.

#+begin_example
  ▸ reviewer-1  read the diff  running 12s
  ✔ auditor-1  check the search code  done 4s
  ⊘ loiterer-1  take far too long  cancelled 30s
  1 running, 3 total
#+end_example

=AiConversation= watches the brigade's =::agent-state-changed= and keeps
one block, rebuilt from the brigade each time --- a reap removes an
agent and there is no state-change event for "gone".

One glyph per state, legible with no colour at all: =▸= working, =✔=
done, =✘= failed, =⊘= stopped, =·= queued.

Two decisions worth knowing:

- *The rows are copies, not references.* A brigade forgets an agent the
  moment its answer is collected, and a panel that emptied itself as
  each result came back would be at its least informative exactly when
  somebody looks at it.
- *Agent state reuses the tool tags* --- =tool-pending=, =tool-ok=,
  =tool-failed= --- rather than adding three of its own. They already
  mean "in flight", "succeeded" and "did not", and a frontend that has
  chosen colours for those renders this block correctly without being
  changed at all.

=/clear= drops the panel and leaves the agents running. See
[[file:agents.org::*Background agents][background agents]].

* Style tags added by the harness layer
| Tag             | Role                                    |
|-----------------+-----------------------------------------|
| =mention=       | an =@path= the user typed               |
| =command=       | a =/name= the user typed                |
| =todo-pending=  | an item not started                     |
| =todo-active=   | the item being worked on                |
| =todo-done=     | a finished item                         |

The first two are for an input line rather than a transcript:
=ai_mention_scan()= is pure and cheap enough to run on every keystroke,
which is what lets a frontend highlight what the pipeline will act on.

* Showing progress
A turn can spend a minute in a tool call, and a frontend that says
nothing during it is indistinguishable from one that has hung.
=AiConversation= folds the same events it folds into blocks into a
one-line description of what is happening:

#+begin_src C
const gchar *doing = ai_conversation_get_activity (conversation);
gint64 elapsed = ai_conversation_get_activity_elapsed (conversation);
#+end_src

| Event                | Activity becomes            |
|----------------------+-----------------------------|
| the turn is sent     | =Waiting for the model=     |
| =THINKING_DELTA=     | =Thinking=                  |
| =TOOL_STARTED=       | =Reading ai-event.c=        |
| =TOOL_FINISHED=      | =Waiting for the model=     |
| =TEXT_DELTA=         | =Responding=                |
| the turn ends        | %NULL                       |

The verb for a tool call comes from =ai_tool_category_gerund()=, next to
the past-tense verb the transcript summary uses --- "Edited" is right for
work that is finished and wrong for work that is happening, and both
belong in the same table.

Watch =notify::activity=. It is emitted when the phrase *changes*, not
per event: a streamed answer is one =TEXT_DELTA= per token, and waking a
frontend fifty times to say "still responding" would cost more than the
turn.

The animation is yours. The library says what is happening; whether that
is a braille spinner, a progress bar or a mode-line string is a decision
only the frontend can make. =ai-tui= draws

#+begin_example
  Grok Build / grok-4.6   ⠹ Running make test… (5s · ^C to stop)
#+end_example

with a 110 ms timer that runs only while =busy= is true --- driven from
=notify::busy= rather than started at each call site, because a turn can
end through its callback, through cancellation or through an error, and a
timer that outlived one of those would animate forever with nothing
behind it.
