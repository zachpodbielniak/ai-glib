* ai-glib Architecture
This document describes the architecture and design of ai-glib.

** Overview
ai-glib is built on GLib/GObject principles, providing:

- Type-safe GObject classes
- Asynchronous operations via GTask
- GObject Introspection support for bindings
- Memory management via g_autoptr and g_steal_pointer

** Interfaces
*** AiProvider
The =AiProvider= interface defines the contract for AI providers:

#+begin_src C
struct _AiProviderInterface
{
    GTypeInterface parent_iface;

    AiProviderType (*get_provider_type)(AiProvider *self);
    const gchar *  (*get_name)(AiProvider *self);
    const gchar *  (*get_default_model)(AiProvider *self);

    void           (*chat_async)(AiProvider *self, ...);
    AiResponse *   (*chat_finish)(AiProvider *self, ...);

    void           (*list_models_async)(AiProvider *self, ...);
    GList *        (*list_models_finish)(AiProvider *self, ...);
};
#+end_src

*** AiStreamable
The =AiStreamable= interface adds streaming support with signals:

- =delta= - Emitted for each text chunk during streaming
- =stream-start= - Emitted when streaming begins
- =stream-end= - Emitted when streaming completes
- =tool-use= - Emitted when a tool use is detected

** Memory Management
ai-glib follows GLib conventions:

1. *g_autoptr()* - Automatic cleanup with scope-based destruction
2. *g_steal_pointer()* - Explicit ownership transfer
3. *(transfer full)* - Caller owns the returned object
4. *(transfer none)* - Caller borrows the reference

*** Example Pattern
#+begin_src C
AiMessage *
ai_message_new_user(const gchar *text)
{
    g_autoptr(AiMessage) self = g_object_new(AI_TYPE_MESSAGE,
                                               "role", AI_ROLE_USER,
                                               NULL);

    g_autoptr(AiTextContent) content = ai_text_content_new(text);
    ai_message_add_content_block(self, (AiContentBlock *)g_steal_pointer(&content));

    return (AiMessage *)g_steal_pointer(&self);
}
#+end_src

** Async Operations
All network operations are asynchronous using GTask:

#+begin_src C
/* Start async operation */
ai_provider_chat_async(provider, messages, system, max_tokens, tools,
                       cancellable, callback, user_data);

/* In callback, get result */
AiResponse *response = ai_provider_chat_finish(provider, result, &error);
#+end_src

** Provider Implementation
Each provider:

1. Extends =AiClient=
2. Implements =AiProvider= interface
3. Implements =AiStreamable= interface
4. Overrides virtual methods for request building and response parsing

*** Virtual Methods
#+begin_src C
struct _AiClientClass
{
    GObjectClass parent_class;

    JsonNode * (*build_request)(AiClient *self, GList *messages, ...);
    AiResponse * (*parse_response)(AiClient *self, JsonNode *json, ...);
    gchar * (*get_endpoint_url)(AiClient *self);
    void (*add_auth_headers)(AiClient *self, SoupMessage *msg);
};
#+end_src

*** Per-Provider Wire-Format Serialization
The in-memory model (=AiMessage=, =AiToolUse=, =AiToolResult=, =AiTextContent=) is provider-agnostic --- callers build messages once and the provider handles the wire-format translation inside =build_request=.

- =AiClaudeClient= consumes =ai_message_to_json()= directly because its output already matches Anthropic's content-block shape.
- =AiOpenAIClient=, =AiGrokClient=, and =AiOllamaClient= share an internal helper, =ai_openai_shared_serialize_messages_array()= (private header =src/providers/ai-openai-shared.h=), that expands one =AiMessage= into one or more OpenAI Chat Completions wire messages --- =role:"tool"= for results, =tool_calls= on assistant messages with =arguments= as a JSON string.
- =AiGeminiClient= walks content blocks inline and emits =parts:[{text | functionCall | functionResponse}]= plus the =tools:[{functionDeclarations:[...]}]= wrapper Gemini expects.

This mirrors pi-mono's per-provider =convertMessages()= pattern. Adding a new provider means writing its own message walker; no central switch needs to know about it.

** Error Handling
Errors use the GLib error domain system:

#+begin_src C
#define AI_ERROR (ai_error_quark())

typedef enum
{
    AI_ERROR_INVALID_API_KEY = 1,
    AI_ERROR_RATE_LIMITED,
    AI_ERROR_NETWORK_ERROR,
    /* ... */
} AiError;
#+end_src

Check errors in callbacks:

#+begin_src C
if (error != NULL)
{
    if (g_error_matches(error, AI_ERROR, AI_ERROR_RATE_LIMITED))
    {
        /* Handle rate limiting */
    }
    return;
}
#+end_src

*** An HTTP failure carries the server's own message
=src/core/ai-http-error.{c,h}= (private) maps a status onto an =AiError=, and every provider goes through it. It exists because the providers each used to map the status and *throw the response body away*, which made a broken model and a broken key look identical:

#+begin_example
  Request failed (HTTP 500)
#+end_example

The body is where the answer is. The same failure now reads:

#+begin_example
  Server error (HTTP 500): llama-server process has terminated:
  GGML_ASSERT(a->ne[2] == b->ne[2]) failed
#+end_example

which names a model that crashes the inference server rather than implying the client is at fault --- that exact confusion is why this exists.

Three rules hold it together:

- *The status picks the code; the body only adds text.* Callers switch on =AI_ERROR_INVALID_API_KEY= to decide whether to re-prompt for a key, so a provider wording its 401 unusually must not change what the error /is/.
- *Every shape the providers actually send is understood*, and anything else degrades rather than disappearing: =error.message= (OpenAI, Grok, Gemini, ollama's OpenAI-compatible endpoint), a bare =error= string (ollama's native endpoints), a top-level =message=, and a bounded raw excerpt when the body is not JSON at all --- an HTML page from a proxy still says =502 Bad Gateway=.
- *An error body is untrusted input.* Members are read through type-checked accessors, never json-glib's =*_member_with_default()=, which emit a critical on a type mismatch: a provider answering =\{"error": \{"message": 500\}\}= must not be able to abort the process on the way to reporting its own error. Messages are bounded so a multi-kilobyte reply does not become the error string.

The streaming paths use =ai_http_error_set_from_stream()=, which does a single bounded read rather than draining to EOF --- an error body is small and already complete by the time the status is known, and a drain would let a server that sends one byte and stalls block the path indefinitely. That path matters most in practice: a streamed chat is where a failing model actually reports itself.

* The view layer
Everything above produces an =AiResponse=. That is enough to print an
answer, and not enough to show a session happening --- which is what a
harness needs.

Two layers sit on top, and the line between them is the design decision
worth knowing about.

#+begin_example
  providers ──emit AiEvent──▶ AiConversation ──folds into──▶ AiTranscript
  (AiEventSource)             (the driver)                   (GListModel<AiViewBlock>)
                                                                     │
                                               ai_view_block_render(block, width)
                                                                     │
                                                     AiRenderedText { text, spans }
                                                         ╱                    ╲
                                             ncurses attr_t          Emacs text properties
#+end_example

*Events* (=src/core/ai-event*.{h,c}=) normalise nine wire formats into one
vocabulary. A provider translates its own output once; nothing downstream
learns what Anthropic SSE or opencode's =={type,part}== envelope looks like.

*The view layer* (=src/view/=) turns that stream into blocks, and each block
into text plus styled spans. It decides that five tool calls read as
=Edited 3 files, ran 2 commands  +21-6=. It does not decide what colour that
is.

A frontend supplies exactly two things: a map from style role to appearance,
and a way to put characters somewhere. =bin/ai-tui.c= does it with ncurses
in about six hundred lines; =examples/transcript-render.c= does it with ANSI
escapes in a hundred. An Emacs frontend replaces that one file and shares
the rest.

See [[file:events.org][The event stream]] and
[[file:transcript.org][The transcript]].

* The harness layer (=src/harness/=)
What a *session* is, as distinct from what a conversation is
(=src/view/=) or what a provider is (=src/providers/=): the commands,
skills and agents on disk, the =@path= mentions in a line of input, and
the completion a frontend offers over both.

#+begin_example
  AiResourceRegistry ──▶ AiCommandSet ──▶ AiCompletionContext
          │                    │                   │
          │                    └── AiConversation ─┘
          │                        send_input_async()
          └──▶ AiToolExecutor (task, skill)
#+end_example

It exists as a layer for the same reason =src/view/= does: an Emacs
frontend has to be able to drive it. A completion popup written in
ncurses is worth nothing to =libreclaw=; =ai_completion_context_query()=
returning a byte range and a candidate list is exactly what
=completion-at-point-functions= consumes.

The search-path table in =ai-resource-registry.c= is the registration
point, the same pattern =AiToolStyle= and =AiImageModelInfo= use.

See [[file:harness.org][The harness layer]].
