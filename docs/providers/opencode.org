* OpenCode Provider
The OpenCode provider (=AiOpenCodeClient=) is a wrapper around the =opencode= CLI tool. It provides access to multiple AI providers (Anthropic, OpenAI, Google) through a unified command-line interface.

** Overview
| Property      | Value                                |
|---------------+--------------------------------------|
| Type          | =AI_PROVIDER_OPENCODE=               |
| Name          | "OpenCode"                           |
| Default Model | =anthropic/claude-sonnet-5=          |
| Interface     | CLI (subprocess)                     |

** Requirements
- The =opencode= CLI must be installed and configured
- The CLI must be available in =$PATH= or specified via environment variable
- API keys for the desired providers must be configured in OpenCode

** Installation
Install the OpenCode CLI following its official documentation.

** Environment Variables
| Variable        | Description                                    |
|-----------------+------------------------------------------------|
| =OPENCODE_PATH= | Override the path to the =opencode= executable |

** Available Models
OpenCode supports models from multiple providers:

*** Anthropic Models
Current generation. Model IDs are passed through to Anthropic verbatim, so
these match the =claude= provider's IDs with an =anthropic/= prefix.

| Define                               | Model ID                       | Description                     |
|--------------------------------------+--------------------------------+---------------------------------|
| =AI_OPENCODE_MODEL_CLAUDE_FABLE_5=   | ="anthropic/claude-fable-5"=   | Most capable                    |
| =AI_OPENCODE_MODEL_CLAUDE_OPUS_5=    | ="anthropic/claude-opus-5"=    | Flagship                        |
| =AI_OPENCODE_MODEL_CLAUDE_SONNET_5=  | ="anthropic/claude-sonnet-5"=  | Balanced (default)              |
| =AI_OPENCODE_MODEL_CLAUDE_HAIKU_4_5= | ="anthropic/claude-haiku-4-5"= | Fastest (there is no Haiku 5)   |

Older generations. The defines are kept for source compatibility, but the
three marked retired name IDs Anthropic has already withdrawn upstream — a
request naming one of them will fail.

| Define                              | Model ID                                | Description                    |
|-------------------------------------+-----------------------------------------+--------------------------------|
| =AI_OPENCODE_MODEL_CLAUDE_OPUS_4_5= | ="anthropic/claude-opus-4-5-20251101"=  | Still available                |
| =AI_OPENCODE_MODEL_CLAUDE_SONNET_4= | ="anthropic/claude-sonnet-4-20250514"=  | Retired 2026-06-15             |
| =AI_OPENCODE_MODEL_CLAUDE_OPUS_4=   | ="anthropic/claude-opus-4-20250514"=    | Retired 2026-06-15             |
| =AI_OPENCODE_MODEL_CLAUDE_HAIKU_3_5=| ="anthropic/claude-3-5-haiku-20241022"= | Retired 2026-02-19             |

*** Anthropic Convenience Alias
| Define                           | Points To                            | Description                |
|----------------------------------+--------------------------------------+----------------------------|
| =AI_OPENCODE_MODEL_CLAUDE_HAIKU= | =AI_OPENCODE_MODEL_CLAUDE_HAIKU_4_5= | Latest Haiku               |

This alias previously expanded to the Haiku 3.5 ID, which is retired; it now
tracks Haiku 4.5. As with the =claude= provider's aliases, =g-ir-scanner=

** Usage
*** Basic Usage
#+begin_src C
#include <ai-glib.h>

int main(void)
{
    g_autoptr(AiOpenCodeClient) client = ai_opencode_client_new();
    g_autoptr(AiMessage) msg = ai_message_new_user("Hello!");
    GList *messages = g_list_append(NULL, msg);

    /* Async chat request */
    ai_provider_chat_async(
        AI_PROVIDER(client),
        messages,
        NULL,  /* system prompt */
        4096,  /* max tokens */
        NULL,  /* tools */
        NULL,  /* cancellable */
        on_chat_complete,
        user_data
    );

    g_list_free(messages);
    return 0;
}
#+end_src

*** Switching Providers
One of the key features of OpenCode is the ability to switch between providers easily:

#+begin_src C
g_autoptr(AiOpenCodeClient) client = ai_opencode_client_new();

/* Use Anthropic Claude */
ai_cli_client_set_model(AI_CLI_CLIENT(client), AI_OPENCODE_MODEL_CLAUDE_SONNET_4);

/* Switch to OpenAI GPT-4o */
ai_cli_client_set_model(AI_CLI_CLIENT(client), AI_OPENCODE_MODEL_GPT_4O);

/* Switch to Google Gemini */
ai_cli_client_set_model(AI_CLI_CLIENT(client), AI_OPENCODE_MODEL_GEMINI_2_FLASH);
#+end_src

*** Streaming
OpenCode supports streaming responses:

#+begin_src C
g_autoptr(AiOpenCodeClient) client = ai_opencode_client_new();

/* Connect to streaming signals */
g_signal_connect(client, "stream-start", G_CALLBACK(on_stream_start), NULL);
g_signal_connect(client, "delta", G_CALLBACK(on_delta), NULL);
g_signal_connect(client, "stream-end", G_CALLBACK(on_stream_end), NULL);

/* Start streaming chat */
ai_streamable_chat_stream_async(
    AI_STREAMABLE(client),
    messages,
    system_prompt,
    max_tokens,
    NULL,  /* tools */
    NULL,  /* cancellable */
    on_stream_complete,
    user_data
);
#+end_src

*** Custom Executable Path
#+begin_src C
g_autoptr(AiOpenCodeClient) client = ai_opencode_client_new();

/* Set custom executable path */
ai_cli_client_set_executable_path(AI_CLI_CLIENT(client), "/opt/opencode/bin/opencode");
#+end_src

** Options
Everything =opencode run= accepts that makes sense headlessly is a GObject
property, so bindings get it natively and the =ai= CLI reaches it through
=--set= without needing a flag of its own.

*** Tool access
#+begin_src C
/* Auto-approve everything not explicitly denied. */
g_object_set(client, "skip-permissions", TRUE, NULL);
#+end_src

This passes =--auto=, opencode's equivalent of Claude Code's
=--dangerously-skip-permissions=, *and* sets =OPENCODE_PERMISSION= in the
child environment. The variable alone used to be the whole mechanism, which
meant a synchronous call never got it: the inherited pipeline spawns without
the client's launcher. The flag closes that gap; the variable stays for
opencode builds that predate it.

As everywhere else, the working directory rather than this property is the
real boundary — see below.

*** Session and run options
| Property             | Flag           | Notes                                                        |
|----------------------+----------------+--------------------------------------------------------------|
| =agent=              | =--agent=      | Which agent to run as                                        |
| =title=              | =--title=      | Session title; otherwise derived from the piped prompt        |
| =files=              | =--file=       | Comma-separated; one =--file= per item                        |
| =share=              | =--share=      | Publishes a shareable link. Off by default                    |
| =continue-session=   | =--continue=   | Resume the most recent session; an explicit session id wins. =ai -p opencode -c= |
| =fork-session=       | =--fork=       | Branch the continued session. Only emitted when there is one  |
| =attach=             | =--attach=     | URL of a running opencode server                              |
| =port=               | =--port=       | Local server port; 0 omits the flag                           |
| =thinking=           | =--thinking=   | Emit reasoning blocks                                         |
| =pure=               | =--pure=       | Run without external plugins                                  |
| =log-level=          | =--log-level=  | =DEBUG=, =INFO=, =WARN=, =ERROR=. Anything else is reported and omitted |
| =print-logs=         | =--print-logs= | Logs to stderr; does not disturb the parsed stdout            |

Credentials for a password-protected =--attach= server are deliberately
*not* properties: an argv is visible to every process on the machine.
opencode reads =OPENCODE_SERVER_USERNAME= and =OPENCODE_SERVER_PASSWORD=
from the environment instead.

*** Working directory
#+begin_src C
ai_cli_client_set_working_directory(AI_CLI_CLIENT(client), "/srv/project");
#+end_src

This does two things: it becomes the child's working directory, and it is
passed as =--dir=, which is what tells opencode which project it is in and
therefore which session store to use. When =attach= is set, =--dir= names a
path on the remote server.

Until recently the directory was applied *only* when =skip-permissions= was
also on — the launcher that carried it was created solely to inject the
permission variable. A caller who named a directory to bound what the CLI
could reach, without also bypassing permissions, got the directory the
parent process happened to start in.

*** From the =ai= CLI
#+begin_example
$ ai -p opencode --skip-permissions "fix the failing test"
$ ai -p opencode --set agent=build --set title=nightly --set pure "run the suite"
$ ai -p opencode --set log-level=DEBUG --set print-logs --dry-run "hi"
#+end_example

** CLI Invocation Details
The prompt is piped on stdin rather than passed as an argument, so it never
appears in the command line or runs into =ARG_MAX=.

#+begin_src sh
opencode run --format json --model anthropic/claude-sonnet-5 --variant medium
#+end_src

=--format= has only two values, =default= and =json=; there is no
=stream-json=. Streaming and non-streaming therefore spawn the *same*
command, and the difference is on this side: the streaming path reads the
JSON events line by line as they arrive instead of waiting for the process
to exit.

Inspect the exact command with:

#+begin_example
$ ai -p opencode --dry-run "hi"
#+end_example

** Response Format
=--format json= produces NDJSON — one JSON event per line, not a single
document:

#+begin_src json
{"type":"step_start","sessionID":"ses_..."}
{"type":"text","part":{"text":"response text"}}
{"type":"tool_use","part":{"tool":"bash","state":{"status":"completed"}}}
{"type":"step_finish","part":{"tokens":{"input":100,"output":50}}}
#+end_src

The parser reads every line, accumulates =text= parts, captures =sessionID=
for session continuity, renders =tool_use= events into a fallback summary,
and takes token counts from =step_finish=. Unparseable lines are skipped:
a plugin writing to stdout should not fail the run.

An error arrives as an =error= member, in one of three shapes — a plain
string, an object with =message=, or opencode's own nesting:

#+begin_src json
{"type":"error","error":{"name":"UnknownError",
                         "data":{"message":"Unexpected server error."}}}
#+end_src

All three are read. The third used to fall through to serialising the whole
object, so a failed run reported raw JSON as its error message instead of
the sentence inside it; it now reports =UnknownError: Unexpected server
error.=

A failing opencode run exits non-zero *and* prints that event on stdout,
with stderr empty. The parsed message therefore takes precedence over the
exit status — see [[../api-reference/ai-cli-client.org][=AiCliClient=]] for how that ordering works.

** Multi-Provider Comparison
Use OpenCode to easily compare responses from different providers:

#+begin_src C
static void
compare_providers(const gchar *prompt)
{
    const gchar *models[] = {
        AI_OPENCODE_MODEL_CLAUDE_SONNET_4,
        AI_OPENCODE_MODEL_GPT_4O,
        AI_OPENCODE_MODEL_GEMINI_2_FLASH,
        NULL
    };

    for (int i = 0; models[i] != NULL; i++)
    {
        g_autoptr(AiOpenCodeClient) client = ai_opencode_client_new();
        ai_cli_client_set_model(AI_CLI_CLIENT(client), models[i]);

        g_print("Testing model: %s\n", models[i]);
        /* Run chat and compare responses... */
    }
}
#+end_src

** Error Handling
#+begin_src C
g_autoptr(GError) error = NULL;
g_autoptr(AiResponse) response = ai_cli_client_chat_sync(
    AI_CLI_CLIENT(client), messages, NULL, &error);

if (error != NULL)
{
    switch (error->code)
    {
        case AI_ERROR_CLI_NOT_FOUND:
            g_printerr("OpenCode CLI not found. Install it or set OPENCODE_PATH.\n");
            break;
        case AI_ERROR_CLI_EXECUTION:
            g_printerr("CLI execution failed: %s\n", error->message);
            break;
        case AI_ERROR_CLI_PARSE_ERROR:
            g_printerr("Failed to parse CLI output: %s\n", error->message);
            break;
        default:
            g_printerr("Error: %s\n", error->message);
            break;
    }
}
#+end_src

** Comparison with HTTP API Providers
| Feature            | HTTP Providers        | OpenCode CLI            |
|--------------------+-----------------------+-------------------------|
| Multiple providers | Separate clients      | Single client           |
| Authentication     | Per-provider API keys | Centralized config      |
| Performance        | Direct HTTP           | Subprocess overhead     |
| Offline capability | No                    | Depends on CLI          |
| Feature parity     | Full                  | Limited to CLI features |

** When to Use OpenCode
- *Multi-provider testing*: Compare responses across different AI providers
- *Centralized configuration*: Manage API keys in one place (the OpenCode config)
- *CLI-first workflows*: When integrating with shell scripts or CLI tools
- *Provider abstraction*: Switch providers without code changes

** Slash commands and mentions
This provider resolves =@= file references and its own slash commands
itself, so ai-glib passes a line through byte-for-byte rather than
expanding first --- doing it twice would be worse than not at all, and
=/compact= and its friends would never arrive.

=AiConversation:passthrough-commands= defaults to =TRUE= here for that
reason. ai-glib's own built-ins (=/help=, =/clear=, =/quit= and the
listings) still run locally, because the wrapped tool has no opinion
about this program's transcript.

See [[file:../harness.org::*Passthrough][the harness layer]].

* Extra MCP servers

opencode has *no* =--mcp-config= flag --- verified against 1.18.18, whose
=run --help= lists none. What it honours is the =OPENCODE_CONFIG= environment
variable naming a JSON file, merged after the global config and before the
project one. That makes it additive and deferential to the user's own
=opencode.json=, the same posture as claude's =--mcp-config= without
=--strict-mcp-config=.

Delivery is therefore an environment variable, which the client sets when it is
handed an =AI_ENDPOINT_KIND_MCP_CONFIG_OPENCODE= endpoint:

#+begin_src c
g_autoptr (AiAgentEndpoint) ep =
  ai_agent_endpoint_new (AI_ENDPOINT_KIND_MCP_CONFIG_OPENCODE, path);

ai_tool_endpoint_consumer_apply (AI_TOOL_ENDPOINT_CONSUMER (client), ep, NULL);
#+end_src

The kind is distinct from =AI_ENDPOINT_KIND_MCP_CONFIG= because the *schema*
differs, not merely the delivery. opencode nests servers under =mcp= and spells
one =\{"type": "local", "command": [...], "environment": \{...\}\}=; a claude-shaped
file handed to opencode is silently ignored. The client refuses the claude kind
rather than accept a file it knows opencode cannot read.

=OPENCODE_CONFIG_CONTENT= would take the JSON inline and is deliberately not
used: it merges at ="local"= scope and so *beats* the user's project config,
which is more authority than a tool injection should take, and a large blob in
the environment adds an =E2BIG= failure mode for nothing.

See [[file:../tools.org][Tools]] for the contract.
