* Claude Code Provider
The Claude Code provider (=AiClaudeCodeClient=) is a wrapper around the =claude= CLI tool from Anthropic. It allows you to use Claude through the command-line interface instead of direct HTTP API calls.

** Overview
| Property      | Value                     |
|---------------+---------------------------|
| Type          | =AI_PROVIDER_CLAUDE_CODE= |
| Name          | "Claude Code"             |
| Default Model | =sonnet=                  |
| Interface     | CLI (subprocess)          |

** Requirements
- The =claude= CLI must be installed and configured
- The CLI must be available in =$PATH= or specified via environment variable

** Installation
Install the Claude CLI following the official instructions from Anthropic. The CLI is part of the Claude Code product.

** Environment Variables
| Variable           | Description                                            |
|--------------------+--------------------------------------------------------|
| =CLAUDE_CODE_PATH= | Override the path to the =claude= executable           |
| =OLLAMA_PATH=      | Override the path to the =ollama= launcher (Ollama transport, below) |

** Available Models
Both forms below are valid =--model= arguments to the =claude= CLI.

The short aliases *float*: the CLI resolves each to the newest model of that
tier, so they follow new releases without a code change.

| Define                         | Model Alias |
|--------------------------------+-------------|
| =AI_CLAUDE_CODE_MODEL_FABLE=   | ="fable"=   |
| =AI_CLAUDE_CODE_MODEL_OPUS=    | ="opus"=    |
| =AI_CLAUDE_CODE_MODEL_SONNET=  | ="sonnet"=  |
| =AI_CLAUDE_CODE_MODEL_HAIKU=   | ="haiku"=   |
| =AI_CLAUDE_CODE_DEFAULT_MODEL= | ="sonnet"=  |

Use a full Claude 5 ID instead to *pin* a generation. 1M context is the
default and the maximum for this generation, so no =[1m]= / =-1m= suffix
exists or is accepted.

| Define                          | Model ID          |
|---------------------------------+-------------------|
| =AI_CLAUDE_CODE_MODEL_FABLE_5=  | ="claude-fable-5"=  |
| =AI_CLAUDE_CODE_MODEL_OPUS_5=   | ="claude-opus-5"=   |
| =AI_CLAUDE_CODE_MODEL_SONNET_5= | ="claude-sonnet-5"= |

=ai_provider_list_models()= reports all seven: the four aliases followed by
the three pinned Claude 5 IDs. The list is advisory --- this provider passes
any =--model= string through to the CLI verbatim without validating it.

** Ollama transport ("ollama/" models)
Ollama can drive the Claude Code CLI as its transport. When the model name
begins with the prefix =ollama/=, this provider does NOT spawn =claude=
directly; instead it spawns:

#+begin_example
ollama launch claude --model <model-after-prefix> -- <the claude args>
#+end_example

For example, model =ollama/glm-5.2:cloud= produces:

#+begin_example
ollama launch claude --model glm-5.2:cloud -- --print --output-format json ...
#+end_example

Notes:
- The =--model= flag is consumed by =ollama launch=; claude's own =--model=
  flag is omitted (the Ollama model id is not a claude alias).
- The =claude= binary must still be installed and on =$PATH= --- =ollama
  launch claude= execs it.
- The launcher binary is =ollama= (override with =OLLAMA_PATH=).
- The prefix match is exact and case-sensitive: =ollama= (no slash) and
  =ollama/= (empty suffix) are NOT the transport and select a normal model.
- Models WITHOUT the =ollama/= prefix are unchanged --- =claude= is spawned
  directly as before.

This is handy for routing local or Ollama-cloud models through the same
Claude Code agent surface. Verify the exact command with the =ai= CLI:
=ai -p claude-code -m ollama/glm-5.2:cloud --dry-run "hi"=.

** Usage
*** Basic Usage
#+begin_src C
#include <ai-glib.h>

int main(void)
{
    g_autoptr(AiClaudeCodeClient) client = ai_claude_code_client_new();
    g_autoptr(AiMessage) msg = ai_message_new_user("Hello, Claude!");
    GList *messages = g_list_append(NULL, msg);

    /* Async chat request */
    ai_provider_chat_async(
        AI_PROVIDER(client),
        messages,
        "You are a helpful assistant.",  /* system prompt */
        4096,                             /* max tokens */
        NULL,                             /* tools */
        NULL,                             /* cancellable */
        on_chat_complete,
        user_data
    );

    g_list_free(messages);
    return 0;
}
#+end_src

*** Setting the Model
#+begin_src C
g_autoptr(AiClaudeCodeClient) client = ai_claude_code_client_new();

/* Use Opus model */
ai_cli_client_set_model(AI_CLI_CLIENT(client), AI_CLAUDE_CODE_MODEL_OPUS);

/* Or use Haiku for faster responses */
ai_cli_client_set_model(AI_CLI_CLIENT(client), AI_CLAUDE_CODE_MODEL_HAIKU);
#+end_src

*** Session Management
Claude Code supports session persistence for multi-turn conversations:

#+begin_src C
g_autoptr(AiClaudeCodeClient) client = ai_claude_code_client_new();

/* Enable session persistence */
ai_cli_client_set_session_persistence(AI_CLI_CLIENT(client), TRUE);

/* After first request, a session ID will be set automatically */
/* You can retrieve it for debugging or logging */
const gchar *session_id = ai_cli_client_get_session_id(AI_CLI_CLIENT(client));

/* Or set a specific session ID to resume a conversation */
ai_cli_client_set_session_id(AI_CLI_CLIENT(client), "previous-session-id");
#+end_src

*** Process Timeout
/Since 0.23.3./ Synchronous chat calls (=ai_cli_client_chat_sync()=) are bounded by a wall-clock deadline, =process-timeout-ms= (default 30 minutes, =0= disables). On expiry the =claude= child process is killed and the call fails with =AI_ERROR_TIMEOUT= --- previously a CLI wedged on a dead network connection could block the calling thread forever. Cancelling the call's =GCancellable= now also kills the child instead of leaking it.

#+begin_src C
g_autoptr(AiClaudeCodeClient) client = ai_claude_code_client_new();

/* Fail any single claude run that takes longer than 10 minutes */
ai_cli_client_set_process_timeout_ms(AI_CLI_CLIENT(client), 600000);
#+end_src

*** Getting Cost Information
Claude Code provides cost information in its responses:

#+begin_src C
static void
on_chat_complete(GObject *source, GAsyncResult *result, gpointer user_data)
{
    g_autoptr(AiResponse) response = ai_provider_chat_finish(
        AI_PROVIDER(source), result, NULL);

    /* Get the cost from the last request */
    gdouble cost = ai_claude_code_client_get_total_cost(
        AI_CLAUDE_CODE_CLIENT(source));
    g_print("Cost: $%.6f USD\n", cost);
}
#+end_src

*** Streaming
Claude Code supports streaming responses:

#+begin_src C
g_autoptr(AiClaudeCodeClient) client = ai_claude_code_client_new();

/* Connect to streaming signals */
g_signal_connect(client, "stream-start", G_CALLBACK(on_stream_start), NULL);
g_signal_connect(client, "delta", G_CALLBACK(on_delta), NULL);
g_signal_connect(client, "stream-end", G_CALLBACK(on_stream_end), NULL);

/* Start streaming chat */
ai_streamable_chat_stream_async(
    AI_STREAMABLE(client),
    messages,
    system_prompt,
    max_tokens,
    NULL,  /* tools */
    NULL,  /* cancellable */
    on_stream_complete,
    user_data
);
#+end_src

** CLI Invocation Details
*** Non-Streaming
#+begin_src sh
claude --print --output-format json \
    --model sonnet \
    --system-prompt-file /tmp/ai-glib-system-prompt-XXXXXX \
    --no-session-persistence \
    "user prompt"
#+end_src

*** Why the system prompt goes in a file

Not =--system-prompt "..."=.  The kernel caps a *single* argv word at
=MAX_ARG_STRLEN= --- 32 pages, 131,072 bytes.  That is not =ARG_MAX=,
which is megabytes, and no headroom in the total buys it back: =execve=
refuses the whole call with =E2BIG= over one long word.

A system prompt is assembled by concatenating an agent's identity files,
so it grows with what the calling product itself writes.  Past that
figure the spawn fails before =claude= runs, and the only thing the
caller sees is:

#+begin_example
Error: Failed to execute child process "…/claude" (Argument list too long)
#+end_example

The user prompt had been moved to stdin for exactly this reason years
earlier.  The rule had been applied to one of the two.

Both prompts are written to files created with =g_file_open_tmp()=, so
mode 0600 and =O_EXCL=: the text is an agent's whole identity and it is
being put in a directory every user on the machine can list.  The files
are removed at the start of the next turn and again when the client is
finalized, so a client that has run a thousand turns holds two files
rather than two thousand.

Unconditionally, not above a size threshold.  A branch that only runs
past 128KB is exercised by nobody until the day it breaks --- which is
how the inline form survived as long as it did.  One path means an
unwritable temporary directory surfaces on the first turn rather than at
scale.

=--system-prompt-file= and =--append-system-prompt-file= are accepted by
the CLI but are *not* in its =--help= flag list; they appear only inside
a description paragraph.  Verified against Claude Code 2.1.247 by
passing each and confirming it is not rejected the way an invented flag
is:

#+begin_example
$ claude --definitely-not-a-flag x --resume <bogus-uuid> --print hi
error: unknown option '--definitely-not-a-flag'

$ claude --system-prompt-file /tmp/sp --resume <bogus-uuid> --print hi
No conversation found with session ID: <bogus-uuid>
#+end_example

** Error Handling
#+begin_src C
g_autoptr(GError) error = NULL;
g_autoptr(AiResponse) response = ai_cli_client_chat_sync(
    AI_CLI_CLIENT(client), messages, NULL, &error);

if (error != NULL)
{
    switch (error->code)
    {
        case AI_ERROR_CLI_NOT_FOUND:
            g_printerr("Claude CLI not found. Install it or set CLAUDE_CODE_PATH.\n");
            break;
        case AI_ERROR_CLI_EXECUTION:
            g_printerr("CLI execution failed: %s\n", error->message);
            break;
        case AI_ERROR_CLI_PARSE_ERROR:
            g_printerr("Failed to parse CLI output: %s\n", error->message);
            break;
        default:
            g_printerr("Error: %s\n", error->message);
            break;
    }
}
#+end_src

** Tool access

The client can grant the CLI its tools two ways.

#+begin_src c
/* The blanket bypass: --dangerously-skip-permissions */
g_object_set(client, "skip-permissions", TRUE, NULL);

/* Narrower: a permission mode plus an allow-list */
g_object_set(client,
             "permission-mode", "acceptEdits",
             "allowed-tools", "Read,Edit,Write",
             "additional-directories", "/srv/reference",
             NULL);
#+end_src

| Property | Flag | Notes |
|---+---+---|
| =skip-permissions= | =--dangerously-skip-permissions= | Wins if both are set, and says so |
| =permission-mode= | =--permission-mode= | =acceptEdits=, =auto=, =bypassPermissions=, =manual=, =dontAsk=, =plan=. An unrecognised value is reported and omitted rather than passed through |
| =allowed-tools= | =--allowedTools= | Comma-separated in, one argv word per tool out |
| =disallowed-tools= | =--disallowedTools= | Same shape |
| =additional-directories= | =--add-dir= | For trees outside the working directory |
| =tools= | =--tools= | Which built-ins exist at all, as opposed to which are pre-approved |

*The working directory is the boundary, not the permission mode.* Every mode
that can write can write anywhere the process can reach, so set
=AiCliClient:working-directory= to bound it:

#+begin_src c
ai_cli_client_set_working_directory(AI_CLI_CLIENT(client), "/srv/project");
#+end_src

Until recently that property had *no effect on this client*: it derives from
=AiCliClient=, whose spawn path applies the directory through a
=GSubprocessLauncher=, but this client built and spawned its own argv with a
bare =g_subprocess_newv()= at three sites and never created a launcher. A
caller that named a directory to bound what the CLI could reach got whatever
directory the parent process was started in. It is applied now.

* Event coverage
On [[file:../events.org][the event stream]] this provider reports text, thinking, tool start, tool arguments, tool results, usage and cost.

True token-level streaming needs =include-partial-messages=; without it the
deltas arrive a whole content block at a time.

** Slash commands and mentions
This provider resolves =@= file references and its own slash commands
itself, so ai-glib passes a line through byte-for-byte rather than
expanding first --- doing it twice would be worse than not at all, and
=/compact= and its friends would never arrive.

=AiConversation:passthrough-commands= defaults to =TRUE= here for that
reason. ai-glib's own built-ins (=/help=, =/clear=, =/quit= and the
listings) still run locally, because the wrapped tool has no opinion
about this program's transcript.

See [[file:../harness.org::*Passthrough][the harness layer]].

* Extra MCP servers through the endpoint interface

This client implements =AiToolEndpointConsumer=, so a host can hand it tools
without knowing which CLI it is. For an =AI_ENDPOINT_KIND_MCP_CONFIG= endpoint
delivery is the =mcp-config-path= property documented above --- the interface is
a second door onto the same state, not a parallel path that could disagree with
it.

Revoking (=ai_tool_endpoint_consumer_clear()=) clears the path, so a later run
cannot point at a config file that has since been deleted.

See [[file:../tools.org][Tools]] for the dialect/delivery split.

** The account's session usage limit

A usage limit is not a failed request. The CLI never contacts the API at
all: it writes one assistant message of its own and exits non-zero. That
message names ~<synthetic>~ as its model and reports every token counter
as zero --- a shape a real completion never produces.

From the exit status alone it is indistinguishable from any other
failure, which is why it used to be retried at once and indefinitely
against a wall that would not move for hours. Measured on a real fleet:
33 attempts in 3 minutes 45 seconds, a median 3.4 seconds apart, every
one of them free of API cost and free of progress.

It is now reported as ~AI_ERROR_SESSION_LIMIT~, and the message carries
the reset time.

*** How it is recognised

~ai_session_limit_looks_synthetic()~ takes the model name and all four
token counters. Both halves are required: the model name alone would
misread anything else a CLI ever labels synthetically, and zero usage
alone is reachable by a completion cut off before it billed. Every cache
counter is included because a turn served from cache reports zero input
and output and has really run --- reading only those two would park a
working agent until a reset that is not coming.

*** The reset time

The text says "resets 6:50pm (America/New_York)": a wall-clock time and
an IANA zone, with *no date*. ~ai_session_limit_parse_reset()~ therefore
returns the next occurrence of that time in that zone, and takes the
current time as a parameter rather than reading the clock --- a function
that reads the clock cannot be tested across a day boundary, and the day
boundary is the case that matters. A limit hit at 23:00 that resets at
06:50 is tomorrow; read as today it would be hours in the past, which
every layer above treats as "already expired".

An unknown zone falls back to local rather than failing. Being an hour
out is a much better answer than reporting no reset, which downstream
reads as a limit that cannot be waited out.

*** Two audiences, one string

The error message carries both a sentence a person reads and a machine
notice a supervisor matches, composed by ai-glib so that whatever logs
the error carries both without having to know it should.

The prose is deliberately *not* machine-readable, and there is a test
saying so. The first version recovered the reset by re-reading the
sentence --- which says "resets *at* 18:50", so the time parser found
the word "at" and returned no reset at all. A supervisor would have seen
"paused" with no time and waited for ever, and nothing would have
reported a fault.

~ai_session_limit_notice_new()~ and ~ai_session_limit_notice_parse()~
are the two halves of the machine format, tested as a round trip,
because halves written apart drift until the watcher silently stops
matching.
