#+title: Agent orchestration
#+description: Running several agents, with budgets, workers and hosts

* What this is

A runtime for coordinating agents: each one a provider plus a tool
executor plus a budget, and a brigade that tracks them.

The library deliberately does not decide *how* an agent runs, *where* its
tools come from, *where* its records live, or *what* it is allowed to
touch. Those are four interfaces the embedding application implements,
because every one of them is a place where a real application already has
opinions and existing machinery.

* Types

| Type               | What it is                                        |
|--------------------+---------------------------------------------------|
| =AiAgent=            | one run: provider, executor, budget, state        |
| =AiBrigade=          | tracks agents, caps concurrency, shares a budget  |
| =AiBudget=           | hard ceilings on tokens, turns, cost and time     |
| =AiPriceTable=       | model rates → integer micro-dollars               |
| =AiMockProvider=     | a scripted provider, for tests                    |

And four interfaces:

| Interface          | Decides                                           |
|--------------------+---------------------------------------------------|
| =AiAgentWorker=      | how an agent executes                             |
| =AiAgentHost=        | what tools it reaches, and how a human is asked   |
| =AiAgentStore=       | where records survive a restart                   |
| =AiAgentIsolation=   | where it is allowed to make a mess                |

=AiLocalWorker= is the one implementation the library ships: it runs an
agent in this process, asynchronously, against the agent's own provider.
That is enough for a terminal frontend or an editor, and it is what
=ai-tui= uses.

* Background agents

The short version: a conversation can start work that outlives the turn
it was asked in, on any provider and any model, and is told when it
finishes.

** Turning it on

Nothing here happens unless the embedding application asks for it. The
library never creates a brigade of its own, because a model able to start
unattended, billable runs is a grant an embedder should make deliberately
--- the same reasoning behind =ai_tool_executor_new_empty()=.

One call does it:

#+begin_src C
ai_conversation_enable_background_agents (conversation, /* max */ 4);
#+end_src

That builds an =AiBrigade= with an =AiLocalWorker=, installs it, and with
it five tools appear on the executor. Assembling the brigade yourself ---
to give it a store, a price table, or a worker that spawns detached
processes --- and calling =ai_conversation_set_brigade()= does the same
job.

To take it away again, pass =NULL=. To keep a brigade for the
application's own purposes while denying the model access to it, clear
the feature bit instead:

#+begin_src C
ai_tool_executor_set_features (executor,
                               ai_tool_executor_get_features (executor) &
                                   ~AI_TOOL_FEATURE_BACKGROUND);
#+end_src

=AiToolFeatures= has two bits, both set by default:

| Bit                          | Tools                                              | Also needs         |
|------------------------------+----------------------------------------------------+--------------------|
| =AI_TOOL_FEATURE_SUBAGENTS=    | =task=, =skill=                                        | a resource registry |
| =AI_TOOL_FEATURE_BACKGROUND=   | =agent_spawn=, =agent_status=, =agent_result=, =agent_wait=, =agent_cancel= | a brigade          |

A bit decides whether a group *may* appear; the thing it runs on decides
whether it does. So an application that sets up neither is unaffected by
any of this, and =tests/test-tool-executor.c= asserts exactly that.

=ai-tui= enables background agents by default, being the reference
frontend; =--no-agents= turns them off.

** Any provider, any model

An agent runs on its own provider. Nothing about it is tied to the
provider of whoever asked for it, which is what makes this work:

#+begin_example
> spawn an agent on claude-code/sonnet to audit the search backends
#+end_example

...in a conversation being held with Grok over HTTP. The =provider= and
=model= parameters go through =ai_provider_factory_new_from_string()=,
the same path =ai -p= and =ai-tui -p= take, so every provider name that
works there works here. Omit them and the agent inherits the
conversation's provider.

An unrecognised provider name is an error, not a redirection ---
=ai_provider_type_from_string()= answers =claude= for anything it does
not know, and an agent quietly running on the wrong model is worse than
a message the model can act on. Naming a model without a provider is
refused for the same reason.

** How it is told

A model exists only between turns, so a turn boundary is the only moment
it can be told anything. The brigade holds each finish until somebody
collects it, and =AiToolExecutor='s run loop collects before every turn
and appends a note:

#+begin_example
Background agent 'reviewer-1' done: audit the search backends

Collect an answer with agent_result, or carry on if it is no longer
relevant.
#+end_example

Two consequences worth knowing:

- *Each finish is reported exactly once.* Draining is destructive, so a
  long conversation does not accumulate the same notice.
- *A final answer is not final while there is news.* If an agent
  finishes while the model is composing what would have been the last
  word, the note is appended and the turn continues. Bounded by the same
  turn limit as everything else.

The note carries *that* an agent finished, never *what it said*. Pasting
a subagent's whole answer into a conversation that has not asked for it
is how delegating a task ends up costing more context than doing it
inline; =agent_result= fetches it when the model decides it wants it.

A frontend does not wait for a turn. =AiConversation::agent-finished=
fires immediately, and =AiViewAgentBlock= --- a panel that updates in
place, like the todo list --- tracks what is running.

** Checking, killing, reaping

| Tool           | Does                                                     |
|----------------+----------------------------------------------------------|
| =agent_spawn=    | starts one and returns its id straight away              |
| =agent_status=   | state, elapsed, turns, tokens, and a peek at the output  |
| =agent_result=   | collects a finished agent's answer and forgets it        |
| =agent_wait=     | blocks until one finishes, with a timeout                |
| =agent_cancel=   | stops one, or =all=                                        |

=agent_status= shows a *peek* --- the first line of what an agent has
written so far --- rather than the whole thing, because the point of
asking is to decide whether to keep waiting, and one agent's half-written
answer in full would crowd out every other row.

=agent_result= reaps: collecting the answer is what ends an agent's life,
so later listings do not grow forever. It refuses an agent that is still
running rather than waiting, because a call that blocks there has stopped
being a caller and become the run.

=agent_wait= is the deliberate block. It waits for a named agent or for
whichever finishes first, up to
=AI_TOOL_EXECUTOR_AGENT_WAIT_MAX_SECONDS= (600). A timeout is *not* an
error: the agent is still working, and the agent is certainly not
stopped by somebody giving up on waiting for it.

A cancelled agent is =cancelled=, not =failed=. Somebody deciding
whether to retry needs to know which happened, so the distinction
survives all the way to the status listing.

** Limits that are load-bearing

- *A background agent may not spawn background agents.* Its executor is
  built without the group. One level of fan-out is delegation; agents
  spawning agents unattended is a fork bomb that bills.
- *Concurrency queues, it does not drop.* Agents beyond
  =max-concurrent= sit in =AI_AGENT_STATE_QUEUED= and are dispatched in
  arrival order as slots free. An agent cancelled while queued is never
  dispatched --- a queue entry is an intention, not a commitment.
- */clear empties the panel and leaves the agents running.* Clearing a
  transcript is an instruction about the display; killing an hour of
  work because somebody wanted a clean screen would be a surprise.
  =ai_brigade_cancel_all()= is how you stop them.

** From the terminal

: /running        what the background agents are doing
: /kill <id|all>  stop one, or all of them

=/agents= is a different thing: it lists the agent *definitions* found on
disk. =/running= is the ones actually running.

* Concurrency

The reason the async executor API exists.

=ai_tool_executor_run()= drives its own nested =GMainLoop=, so two
conversations at once meant two threads. =ai_tool_executor_run_async()=
leaves callbacks pending on the caller's context instead, and N
concurrent runs are N sets of pending callbacks on one thread.

*One executor supports one run at a time* — it holds the tool list and
the active provider for the duration. That is why an agent owns its own
executor rather than sharing one, and it is also what makes an allowlist
structural: an agent is handed an executor built from what it may call,
so calling anything else is not refused, it is unrepresentable.

* Budgets

Ceilings, not guidance. An agent that reaches one stops.

Both levels are enforced: an agent's own budget catches one runaway,
while the brigade's shared budget catches fifty well-behaved agents that
add up to too much. Neither subsumes the other.

Cost is carried in micro-dollars as a =gint64=, because it is summed
across thousands of turns and floating point drift in the one figure a
limit acts on would be the worst place for it. A model with no price is
reported as *unpriced*, never as free — the two are indistinguishable
once summed, and treating unknown as free silently understates spend.

* Why =AiAgentWorker= is an interface

So that a job registry which double-forks detached processes and tracks
them with sentinel files becomes *an implementation*, rather than a
special case threaded through the orchestrator.

Such a worker cannot push: its children are reparented to init, so no
=SIGCHLD= reaches the spawning process and there is no completion
callback to hook. It implements =poll_state= and the brigade sweeps it.
An in-process worker leaves =poll_state= NULL and simply emits
=AiAgent::state-changed=. =ai_brigade_sweep()= is harmless when nothing
needs polling.

=AI_AGENT_STATE_INTERRUPTED= exists for the same reason. An agent that
was running when the process stopped did not fail and did not finish;
saying so is what stops anything resuming work whose outcome nobody
observed.

* Testing

=AiMockProvider= ships in the library rather than the test suite, because
anything embedding ai-glib has the same problem the library does:
exercising a tool loop without a network, an API key or a bill.

Until it existed the multi-turn loop had *no test at all*.

#+begin_src c
g_autoptr(AiMockProvider) mock = ai_mock_provider_new();

ai_mock_provider_push_tool_use(mock, "echo", "{\"text\":\"hi\"}");
ai_mock_provider_push_text(mock, "all done");

ai_tool_executor_run_async(exec, AI_PROVIDER(mock), messages,
                           NULL, 0, /* max_turns */ 5, NULL, cb, data);
#+end_src

Set a delay to make concurrency observable — without one, each run
finishes before the next starts and nothing actually overlaps.

* Turn limits

=max_turns= counts provider round trips, which is the thing that costs
money, and fires on receiving the Nth. A cap of 3 means three requests
were made and the third reply was refused rather than acted on, so two
tool calls ran.

It is a parameter rather than a constant because an orchestrator budgets
turns per agent, and a limit the caller cannot set is one they have to
work around.

* Agents from disk
Separately from =AiAgent= and =AiBrigade=, which orchestrate runs this
program starts, ai-glib reads the agent *files* other harnesses keep ---
=~/.claude/agents/*.md=, =.opencode/agent/*.md= and friends.

Give an executor a resource registry and the model gains a =task= tool
that runs one:

#+begin_src C
ai_tool_executor_set_resource_registry (executor, registry);
#+end_src

The subagent runs with the agent file's body as its system prompt and
*only* the tools its =tools:= list declares --- the child executor is
built without the others, so calling one is not refused, it is
unrepresentable. Recursion is capped at
=AI_TOOL_EXECUTOR_MAX_TASK_DEPTH=, and the refusal is reported to the
model so it does the work itself rather than wondering why nothing
happened.
